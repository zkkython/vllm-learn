# 课时4 - vLLM 核心组件-调度器如何实现

> **关键源码文件**：
> - `vllm/vllm/v1/core/sched/scheduler.py` -- `Scheduler` 主实现，负责请求入队、调度、抢占、执行后状态更新
> - `vllm/vllm/v1/core/sched/output.py` -- `SchedulerOutput`、`NewRequestData`、`CachedRequestData`，定义调度器输出格式

> - `vllm/vllm/v1/request.py` -- `Request` 对象，保存 prompt、输出 token、状态、优先级、block hash 等信息
> - `vllm/vllm/v1/core/kv_cache_manager.py` -- 调度器通过它申请和释放 KV Cache block

## 学习目标

1. 理解 vLLM 调度器为什么同时维护 `waiting` 和 `running` 两类请求队列
2. 掌握 `Scheduler.add_request()`、`schedule()`、`update_from_output()` 三个核心入口的职责分工
3. 理解调度器如何先调度 `running` 队列，再调度 `waiting` 队列，并在显存不足时执行抢占
4. 掌握 `SchedulerOutput` 为什么要拆成 `scheduled_new_reqs` 和 `scheduled_cached_reqs`
5. 能够从源码层面串起一次 `请求入队 -> 调度 -> 模型执行 -> 后处理 -> 请求完成/回收` 的完整闭环

## 4.1 调度器 Demo

### 原理讲解

调度器的目标并不是“尽可能多跑请求”这么简单，它要同时满足四个约束：

1. **token budget 约束**：本轮最多只能调度 `max_num_batched_tokens`
2. **并发请求数约束**：`running` 队列不能超过 `max_num_seqs`
3. **显存约束**：每轮调度前要确认 KV Cache 是否还能分配 block
4. **公平性 / 优先级约束**：waiting 队列不能永远饥饿，priority 模式下高优请求要能插队

因此，调度器的工作并不是“按请求粒度排队”，而是“按 token 粒度分配本轮执行预算”。

在 vLLM V1 中，这件事集中落在 `Scheduler.schedule()` 中。它会：

- 先看 `running` 队列里哪些请求还需要继续算 token
- 再看 `waiting` 队列里能否拉新请求进来
- 生成 `SchedulerOutput`
- 交给 `Executor -> Worker -> ModelRunner` 去执行

可以先把它想成一个“每轮做一次账”的系统。

### 源码解析

**1. `Scheduler` 初始化时就把调度约束和两个队列准备好**

```python
# vllm/vllm/v1/core/sched/scheduler.py :: Scheduler.__init__
self.max_num_running_reqs = self.scheduler_config.max_num_seqs
self.max_num_scheduled_tokens = self.scheduler_config.max_num_batched_tokens

self.requests: dict[str, Request] = {}
self.waiting = create_request_queue(self.policy)
self.running: list[Request] = []
```

这说明调度器内部至少有三份核心状态：

- `requests`：全量请求字典，便于按 `req_id` 回查
- `waiting`：尚未进入执行的请求
- `running`：已经拿到 KV Cache、可以继续跑的请求

**2. `SchedulerOutput` 是调度器和执行器之间的接口层**

```python
# vllm/vllm/v1/core/sched/output.py :: SchedulerOutput
@dataclass
class SchedulerOutput:
    scheduled_new_reqs: list[NewRequestData]
    scheduled_cached_reqs: CachedRequestData
    num_scheduled_tokens: dict[str, int]
    total_num_scheduled_tokens: int
    scheduled_spec_decode_tokens: dict[str, list[int]]
    scheduled_encoder_inputs: dict[str, list[int]]
    num_common_prefix_blocks: list[int]
    finished_req_ids: set[str]
```

为什么这里要区分 `new` 和 `cached`？

- 新请求第一次进入 Worker，需要把完整请求信息都发过去
- 老请求 Worker 侧已经缓存过，只要发差量即可

所以这不是“为了数据结构好看”，而是为了减少跨进程通信量。

**3. waiting 队列的具体实现由策略决定**

```python
# vllm/vllm/v1/core/sched/request_queue.py :: create_request_queue
if policy == SchedulingPolicy.PRIORITY:
    return PriorityRequestQueue()
elif policy == SchedulingPolicy.FCFS:
    return FCFSRequestQueue()
```

也就是说，`Scheduler` 本身不关心底层是 deque 还是 heap，它只依赖抽象队列接口。

### 代码示例

下面给一个最小调度器 demo，只保留 `waiting/running/token_budget` 这三个核心概念：

```python
from dataclasses import dataclass


@dataclass
class Req:
    req_id: str
    remain_tokens: int


class SimpleScheduler:
    def __init__(self, max_tokens: int, max_running: int):
        self.max_tokens = max_tokens
        self.max_running = max_running
        self.waiting = []
        self.running = []

    def add_request(self, req: Req):
        self.waiting.append(req)

    def schedule(self):
        token_budget = self.max_tokens
        scheduled = {}

        for req in list(self.running):
            if token_budget == 0:
                break
            step_tokens = min(req.remain_tokens, token_budget)
            scheduled[req.req_id] = step_tokens
            req.remain_tokens -= step_tokens
            token_budget -= step_tokens

        while self.waiting and len(self.running) < self.max_running and token_budget > 0:
            req = self.waiting.pop(0)
            step_tokens = min(req.remain_tokens, token_budget)
            scheduled[req.req_id] = step_tokens
            req.remain_tokens -= step_tokens
            token_budget -= step_tokens
            self.running.append(req)

        self.running = [req for req in self.running if req.remain_tokens > 0]
        return scheduled


scheduler = SimpleScheduler(max_tokens=6, max_running=2)
scheduler.add_request(Req("req1", 4))
scheduler.add_request(Req("req2", 5))
print(scheduler.schedule())  # {'req1': 4, 'req2': 2}
```

### 架构总览

```text
                   调度器在 vLLM 中的位置
  ====================================================================

  add_request()
       |
       v
  waiting queue
       |
       | schedule()
       v
  running queue + token budget + KV cache budget
       |
       v
  SchedulerOutput
       |
       v
  Executor / Worker / ModelRunner
       |
       v
  ModelRunnerOutput
       |
       v
  update_from_output()
```

## 4.2 增加请求到调度器

### 原理讲解

新请求进入调度器时，最重要的不是“立刻执行”，而是先把它变成统一的内部对象 `Request`，再挂到 waiting 队列。

这个步骤看起来简单，实际上承担了三个作用：

1. 保存请求的静态信息：prompt、sampling params、arrival time、priority
2. 计算后续调度要用的衍生信息：`num_prompt_tokens`、`block_hashes`
3. 把请求正式纳入 scheduler 的生命周期管理

也就是说，请求一旦进了 `Scheduler`，后面无论是调度、抢占、停止还是释放，都是围绕这个 `Request` 对象进行。

### 源码解析

**1. `Request` 负责把用户输入变成调度态对象**

```python
# vllm/vllm/v1/request.py :: Request.__init__
self.request_id = request_id
self.priority = priority
self.sampling_params = sampling_params
self.arrival_time = arrival_time if arrival_time is not None else time.time()

self.status = RequestStatus.WAITING
self.prompt_token_ids = prompt_token_ids
self.num_prompt_tokens = length_from_prompt_token_ids_or_embeds(
    prompt_token_ids, prompt_embeds
)
self._output_token_ids = []
self._all_token_ids = self.prompt_token_ids.copy() if self.prompt_token_ids is not None else [0] * self.num_prompt_tokens
```

从这里可以看出，`Request` 不是纯数据包，它已经预留了：

- 输出 token 存储
- 当前状态
- 后续 block hash / prefix cache 所需信息

**2. `Scheduler.add_request()` 本身非常薄**

```python
# vllm/vllm/v1/core/sched/scheduler.py :: Scheduler.add_request
def add_request(self, request: Request) -> None:
    self.waiting.add_request(request)
    self.requests[request.request_id] = request
    if self.log_stats:
        request.record_event(EngineCoreEventType.QUEUED)
```

它只做三件事：

- 入 waiting 队列
- 进全局字典
- 记录排队事件

这说明：**请求初始化和调度入队是两个阶段。**

**3. priority 模式依赖 `Request.__lt__`**

```python
# vllm/vllm/v1/request.py :: Request.__lt__
if self.priority != other.priority:
    return self.priority < other.priority
if self.arrival_time != other.arrival_time:
    return self.arrival_time < other.arrival_time
```

所以 priority 调度并不是单靠 queue 组件实现的，而是 `Request` 自己定义了“谁更靠前”。

### 代码示例

```python
import time
from dataclasses import dataclass, field


@dataclass(order=True)
class Req:
    priority: int
    arrival_time: float = field(default_factory=time.time)
    req_id: str = ""
    prompt: str = ""


class SimpleScheduler:
    def __init__(self):
        self.waiting = []
        self.requests = {}

    def add_request(self, req: Req):
        self.waiting.append(req)
        self.requests[req.req_id] = req
        self.waiting.sort()


s = SimpleScheduler()
s.add_request(Req(priority=1, req_id="req_low", prompt="hello"))
s.add_request(Req(priority=0, req_id="req_high", prompt="world"))
print([req.req_id for req in s.waiting])  # ['req_high', 'req_low']
```

## 4.3 调度器调度 running 队列

### 原理讲解

`running` 队列里的请求不是“已经完成的请求”，而是“已经进入持久执行态”的请求。

这类请求通常已经具备：

- 已分配的 KV Cache block
- 已知的 `num_computed_tokens`
- 已经缓存到 Worker 侧的请求元信息

因此，在调度 `running` 队列时，调度器关心的不是“能不能进来”，而是：

1. 本轮还欠多少 token 没算
2. 这些 token 是否还在 `max_model_len` 之内
3. 是否还能继续申请 KV Cache slot
4. 如果 slot 不够，应该抢占谁

所以 `running` 队列调度的本质是：**在有限 token budget 和显存 budget 下，把老请求继续往前推。**

### 源码解析

**1. `schedule()` 先处理 `running` 队列**

```python
# vllm/vllm/v1/core/sched/scheduler.py :: Scheduler.schedule
req_index = 0
while req_index < len(self.running) and token_budget > 0:
    request = self.running[req_index]
    ...
```

这说明 vLLM 的默认策略是：

- 先尽可能让已经在跑的请求继续推进
- 再考虑 waiting 队列里有没有新请求能塞进来

**2. 本轮要给一个 running 请求分配多少 token**

```python
num_new_tokens = (
    request.num_tokens_with_spec
    + request.num_output_placeholders
    - request.num_computed_tokens
)
num_new_tokens = min(num_new_tokens, token_budget)
num_new_tokens = min(
    num_new_tokens, self.max_model_len - 1 - request.num_computed_tokens
)
```

这段很关键，它说明调度器不是按“请求数”调度，而是按“请求当前还差多少 token”调度。

**3. 真正卡显存的是 `allocate_slots()`**

```python
new_blocks = self.kv_cache_manager.allocate_slots(
    request,
    num_new_tokens,
    num_lookahead_tokens=self.num_lookahead_tokens,
)
```

如果返回 `None`，说明这个请求本轮没法继续扩容 block。

**4. 显存不足时执行抢占**

```python
if new_blocks is None:
    if self.policy == SchedulingPolicy.PRIORITY:
        preempted_req = max(
            self.running,
            key=lambda r: (r.priority, r.arrival_time),
        )
    else:
        preempted_req = self.running.pop()

    self._preempt_request(preempted_req, scheduled_timestamp)
```

这里体现了调度器的关键设计：

- 显存不够时，不是“本轮直接失败”
- 而是优先释放低优先级或末尾请求，给更值得继续跑的请求让路

**5. 抢占本质上是“释放 block + 回 waiting”**

```python
# vllm/vllm/v1/core/sched/scheduler.py :: Scheduler._preempt_request
self.kv_cache_manager.free(request)
self.encoder_cache_manager.free(request)
request.status = RequestStatus.PREEMPTED
request.num_computed_tokens = 0
self.waiting.prepend_request(request)
```

抢占不是删除请求，而是把它打回 waiting，等待以后重新进入。

### 代码示例

```python
from dataclasses import dataclass


@dataclass
class Req:
    req_id: str
    priority: int
    remain_tokens: int


def schedule_running(running, token_budget, free_slots):
    scheduled = {}
    preempted = []

    idx = 0
    while idx < len(running) and token_budget > 0:
        req = running[idx]
        need = min(req.remain_tokens, token_budget)
        if free_slots <= 0:
            victim = max(running, key=lambda r: r.priority)
            running.remove(victim)
            preempted.append(victim.req_id)
            if victim is req:
                break
            continue

        scheduled[req.req_id] = need
        req.remain_tokens -= need
        token_budget -= need
        free_slots -= 1
        idx += 1

    return scheduled, preempted


running = [Req("req1", 0, 4), Req("req2", 2, 3)]
print(schedule_running(running, token_budget=4, free_slots=1))
```

### 数据流图

```text
               running 队列调度主链
  ====================================================================

  running requests
       |
       v
  计算 num_new_tokens
       |
       v
  KVCacheManager.allocate_slots()
       |
       +--> 成功: 记录 req_to_new_blocks / num_scheduled_tokens
       |
       +--> 失败: _preempt_request()
                   - free KV blocks
                   - status = PREEMPTED
                   - 回 waiting
```

## 4.4 调度器调度 waiting 队列

### 原理讲解

`waiting` 队列是新请求和被抢占请求的入口。

和 `running` 队列相比，调度 waiting 时要额外做几件事：

1. 判断这个请求当前是否允许进入执行
2. 看它有没有 prefix cache 命中
3. 看它是否需要 encoder budget、LoRA budget、remote KV budget
4. 给它第一次分配 block
5. 决定它属于 `scheduled_new_reqs` 还是 `scheduled_resumed_reqs`

因此，waiting 队列调度比 running 更像“准入控制”。

### 源码解析

**1. waiting 只有在没有新抢占时才继续调度**

```python
# vllm/vllm/v1/core/sched/scheduler.py :: Scheduler.schedule
if not preempted_reqs:
    while self.waiting and token_budget > 0:
        if len(self.running) == self.max_num_running_reqs:
            break
```

也就是说，如果 running 队列刚刚因为显存紧张发生了抢占，本轮通常不再继续拉新请求。

**2. 先看 prefix cache 命中**

```python
new_computed_blocks, num_new_local_computed_tokens = (
    self.kv_cache_manager.get_computed_blocks(request)
)
```

这一步的意义是：

- 如果 prompt 前缀已经命中缓存，不需要从头重算
- 调度器可以直接把“已命中的 block”计入请求状态

**3. 再决定本轮真正要调度多少 token**

```python
num_new_tokens = request.num_tokens - num_computed_tokens
if 0 < threshold < num_new_tokens:
    num_new_tokens = threshold
num_new_tokens = min(num_new_tokens, token_budget)
```

所以 waiting 请求第一次调度，也不一定是整段 prompt 一次性全算完；如果 chunked prefill 开着，它完全可能被切块。

**4. 最终还是通过 `allocate_slots()` 判断能否落地**

```python
new_blocks = self.kv_cache_manager.allocate_slots(
    request,
    num_new_tokens + num_external_computed_tokens,
    num_new_local_computed_tokens,
    new_computed_blocks,
    ...
)
if new_blocks is None:
    break
```

**5. 真正进入 running 后，区分 new 和 resumed**

```python
if request.status == RequestStatus.WAITING:
    scheduled_new_reqs.append(request)
elif request.status == RequestStatus.PREEMPTED:
    scheduled_resumed_reqs.append(request)
```

这一步会直接影响后面构造 `SchedulerOutput` 的方式。

### 代码示例

```python
from dataclasses import dataclass


@dataclass
class Req:
    req_id: str
    total_tokens: int
    cached_tokens: int = 0
    status: str = "WAITING"


def schedule_waiting(waiting, token_budget, max_running, running):
    scheduled_new = []
    while waiting and token_budget > 0 and len(running) < max_running:
        req = waiting.pop(0)
        num_new_tokens = req.total_tokens - req.cached_tokens
        step_tokens = min(num_new_tokens, token_budget)
        token_budget -= step_tokens
        req.status = "RUNNING"
        running.append(req)
        scheduled_new.append((req.req_id, step_tokens, req.cached_tokens))
    return scheduled_new


waiting = [Req("req1", 8, cached_tokens=4), Req("req2", 6, cached_tokens=0)]
running = []
print(schedule_waiting(waiting, token_budget=6, max_running=2, running=running))
```

### 架构总览

```text
                  waiting 队列调度主链
  ====================================================================

  waiting queue
       |
       v
  peek_request()
       |
       +--> prefix cache hit? -> get_computed_blocks()
       |
       +--> LoRA / encoder / connector 约束检查
       |
       v
  allocate_slots()
       |
       +--> 失败: 本轮停止继续拉新
       |
       +--> 成功: 进入 running
                   - WAITING  -> scheduled_new_reqs
                   - PREEMPTED -> scheduled_resumed_reqs
```

## 4.5 调度执行之后的后处理

### 原理讲解

调度器的工作并没有在 `schedule()` 返回时结束。

一轮执行之后，它还要做两类后处理：

1. **调度后立即更新账本**：本轮已经发出去多少 token，要先把 `num_computed_tokens` 往前推进
2. **模型执行完成后收结果**：把 `ModelRunnerOutput` 变成 `EngineCoreOutput`，并决定哪些请求完成、哪些请求继续留在 running

如果只做前半段，不做后半段，调度器就不知道请求是否真正停止、是否需要释放 KV Cache、是否要把输出返给前端。

### 源码解析

**1. `schedule()` 末尾会先调用 `_update_after_schedule()`**

```python
# vllm/vllm/v1/core/sched/scheduler.py :: Scheduler.schedule
self._update_after_schedule(scheduler_output)
return scheduler_output
```

它的核心逻辑是：

```python
for req_id, num_scheduled_token in num_scheduled_tokens.items():
    request = self.requests[req_id]
    request.num_computed_tokens += num_scheduled_token
```

也就是说，调度器在“发车”之后，就会先把账本往前记一笔。

**2. 真正的执行后处理在 `update_from_output()`**

```python
# vllm/vllm/v1/core/sched/scheduler.py :: Scheduler.update_from_output
for req_id, num_tokens_scheduled in num_scheduled_tokens.items():
    request = self.requests.get(req_id)
    ...
    generated_token_ids = sampled_token_ids[req_index] if sampled_token_ids else []
    ...
    if new_token_ids:
        new_token_ids, stopped = self._update_request_with_output(
            request, new_token_ids
        )
    ...
    if stopped:
        kv_transfer_params = self._free_request(request)
```

这里有三个关键动作：

- 把新 token 追加到 `Request`
- 检查 stop condition
- 对完成请求执行释放

**3. `_update_request_with_output()` 负责 trim + stop 检查**

```python
for num_new, output_token_id in enumerate(new_token_ids, 1):
    request.append_output_token_ids(output_token_id)
    stopped = check_stop(request, self.max_model_len)
    if stopped:
        del new_token_ids[num_new:]
        break
```

这说明“模型吐了 token”不代表这些 token 一定都能返回给用户；如果中途命中 stop string / max length，后面的 token 会被裁掉。

**4. `_free_request()` 负责清理请求生命周期**

```python
def _free_request(self, request: Request) -> dict[str, Any] | None:
    self.encoder_cache_manager.free(request)
    self.finished_req_ids.add(request.request_id)
    if not delay_free_blocks:
        self._free_blocks(request)
```

所以请求完成时的清理不是只删一个字典键，而是：

- 释放 encoder cache
- 标记 finished req ids
- 释放 KV blocks
- 从 `requests` 字典删除

**5. 最终组装成 `EngineCoreOutputs` 返回前端**

```python
engine_core_outputs = {
    client_index: EngineCoreOutputs(outputs=outs)
    for client_index, outs in outputs.items()
}
```

这一步让调度器成为“内部执行结果”和“前端输出协议”之间的桥梁。

### 代码示例

```python
from dataclasses import dataclass


@dataclass
class Req:
    req_id: str
    output_tokens: list[str]
    finished: bool = False


def update_request_with_output(req: Req, new_tokens, stop_token="."):
    returned = []
    for token in new_tokens:
        req.output_tokens.append(token)
        returned.append(token)
        if token == stop_token:
            req.finished = True
            break
    return returned, req.finished


req = Req("req1", [])
print(update_request_with_output(req, ["hello", "world", "."]))
print(req)
```

### 完整流程图

```text
            调度后处理与执行后处理的完整闭环
  =========================================================================

  schedule()
    |
    | _update_after_schedule()
    |   -> request.num_computed_tokens += scheduled_tokens
    v
  SchedulerOutput
    |
    v
  ModelRunnerOutput
    |
    v
  update_from_output()
    |
    | _update_request_with_output()
    |   -> append_output_token_ids()
    |   -> check_stop()
    |
    | if stopped:
    |   -> _free_request()
    v
  EngineCoreOutputs
    |
    v
  前端 OutputProcessor / 用户流式输出
```

---

## 总结

本章重点拆开了 vLLM 调度器的完整闭环：

1. **调度器维护两类核心队列**：`waiting` 负责准入，`running` 负责持续推进
2. **请求进入调度器的入口很薄**：`Scheduler.add_request()` 只是入队和登记，真正复杂的是后续调度
3. **`running` 队列优先级更高**：调度器会先尽量推进已经在跑的请求，并在显存不足时执行抢占
4. **`waiting` 队列承担准入控制**：prefix cache、LoRA、encoder budget、KV transfer 等约束都在这里被检查
5. **`SchedulerOutput` 是执行层接口**：它把新请求和已缓存请求区分开，显著减少跨进程通信量
6. **后处理同样关键**：`_update_after_schedule()` 和 `update_from_output()` 共同维护请求生命周期，决定 token 追加、停止、回收和最终输出

1. **为什么 vLLM 调度器要先调度 `running` 队列，再调度 `waiting` 队列？** 这种顺序对吞吐和时延分别有什么影响？

2. **`SchedulerOutput` 为什么要拆成 `scheduled_new_reqs` 和 `scheduled_cached_reqs`？** 如果所有请求都统一发送完整信息，会在哪个环节产生明显额外开销？
