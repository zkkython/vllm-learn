## 12.1 DP 概述

### 原理讲解

在推理场景里，数据并行（DP）的核心作用不是“切模型”，而是：

**复制多份模型副本，让不同请求分流到不同副本上，从而提升整体吞吐。**

这和张量并行（TP）很不一样：

- **TP**：把同一个模型层拆到多张卡上，一次 forward 需要多卡协作
- **DP**：每个 rank 各自有一份完整模型副本，不同 rank 处理不同请求

因此，推理里的 DP 最常见的收益是：

1. 吃掉更多并发请求
2. 在多副本间做流量分摊
3. 在 MoE、混合并行等场景下组合出更大的系统规模

但它也有代价：

- 每个 DP rank 都要放一份模型副本
- 单个请求的显存压力不会因为 DP 自动降低

### 源码解析

在 vLLM 里，DP 的最上层入口都集中在 `ParallelConfig`：

```python
class ParallelConfig:
    data_parallel_size: int = 1
    data_parallel_rank: int = 0
    data_parallel_size_local: int = 1
    data_parallel_backend: DataParallelBackend = "mp"
    data_parallel_external_lb: bool = False
    data_parallel_hybrid_lb: bool = False
```

这几个字段基本已经把 vLLM 的 DP 场景说清楚了：

- `data_parallel_size`：总共有多少个 DP 副本
- `data_parallel_rank`：当前副本是第几个
- `data_parallel_size_local`：本机上有多少个 DP 副本
- `external_lb / hybrid_lb`：在线服务下的负载均衡模式

再看 `world_size_across_dp`：

```python
@property
def world_size_across_dp(self) -> int:
    return self.world_size * self.data_parallel_size
```

这说明在 vLLM 的世界里：

- `world_size` 通常是 `TP x PP x PCP`
- 再乘上 `DP` 才是跨 DP 的完整世界大小

### 代码示例

下面用最小例子说明推理 DP 的本质：把不同 prompt 分给不同副本。

```python
prompts = ["p0", "p1", "p2", "p3", "p4"]
dp_size = 2


def shard_prompts(rank):
    return [p for i, p in enumerate(prompts) if i % dp_size == rank]


print("rank0:", shard_prompts(0))
print("rank1:", shard_prompts(1))
```

这个思路和训练里的 sample sharding 很像，但这里关注的是 **推理请求分流**。

## 12.2 DP 逻辑框架和流程图

### 原理讲解

vLLM 的 DP 逻辑，不只是“多开几个进程”这么简单，它至少包含三层：

1. **分布式环境初始化**
2. **不同并行维度的 group 划分**
3. **请求级或 batch 级的协调**

对于推理来说，最容易忽略的是第 3 层。

因为即使每个 DP rank 各跑自己的请求，某些场景下仍然需要跨 rank 同步一些轻量元信息，比如：

- 当前 batch 的 token 数
- cudagraph padding 大小
- 在线服务里的全局 running/paused 状态

### 源码解析

**1. `init_distributed_environment()` 会把 DP 维度并进全局 world**

```python
# vllm/vllm/distributed/parallel_state.py
rank = parallel_config.data_parallel_rank * world_size + rank
world_size = parallel_config.world_size_across_dp
```

这一步的意义是：

- 原本只考虑 TP/PP 的局部 rank/world_size
- 在初始化分布式环境时扩展成包含 DP 的全局 rank/world_size

**2. `initialize_model_parallel()` 会按 `ExternalDP x DP x PP x TP` 划分 group**

```python
all_ranks = torch.arange(world_size).reshape(
    -1,
    data_parallel_size,
    pipeline_model_parallel_size,
    prefill_context_model_parallel_size,
    tensor_model_parallel_size,
)
```

这是第12章最值得记住的一行之一。因为它直接告诉你：

**vLLM 是先把全局 rank 张量化，再按不同维度转置/reshape 去切组。**

随后它会分别创建：

- `_TP`
- `_PP`
- `_DP`
- `_EP`
- `_DCP`
- `_PCP`

其中 `_DP` 是这样切的：

```python
group_ranks = all_ranks.transpose(1, 4).reshape(-1, data_parallel_size).unbind(0)
_DP = init_model_parallel_group(..., group_name="dp")
```

**3. worker 侧会用 `dp_utils.py` 同步本轮 batch 元信息**

```python
tensor = torch.zeros(2, dp_size, dtype=torch.int32, device="cpu")
tensor[0][dp_rank] = num_tokens
tensor[1][dp_rank] = cudagraph_size
dist.all_reduce(tensor, group=group)
```

这里同步的不是大张量，而是：

- 每个 rank 当前要跑多少 token
- 当前 rank 能不能命中某个 cudagraph size

这说明推理 DP 的同步重点更多是 **控制元信息**，而不是像训练那样同步梯度。

**4. 在线服务场景还会多一个 `DPCoordinator`**

`v1/engine/coordinator.py` 里的 `DPCoordinator` 负责：

- 收集不同 DP engine 的等待队列和运行队列状态
- 维护当前 request wave
- 在必要时广播 `START_DP_WAVE`

这层主要服务在线多实例负载均衡。

### 代码示例

下面用极简伪代码模拟“同步本轮 token 数”的逻辑：

```python
dp_rank_num_tokens = {0: 16, 1: 24, 2: 0}

max_tokens = max(dp_rank_num_tokens.values())
can_use_graph = all(x > 0 for x in dp_rank_num_tokens.values())

print("同步后的最大 token 数:", max_tokens)
print("所有 rank 是否都能继续一起跑:", can_use_graph)
```

### 流程图

```text
                 vLLM 推理 DP 逻辑框架
========================================================================

ParallelConfig
   |
   v
init_distributed_environment()
   |
   v
initialize_model_parallel()
   |
   +--> TP group
   +--> PP group
   +--> DP group
   +--> EP group
   |
   v
请求进入各 DP rank
   |
   +--> 离线: 由用户/脚本自行切分 prompts
   +--> 在线: 由 coordinator / LB 决定路由
   |
   v
dp_utils 同步轻量 batch 元信息
   |
   v
各 rank 执行本地 forward
```

## 12.3 DP 如何部署模型

### 原理讲解

在 vLLM 里，DP 部署常见有三种形态：

1. **离线多进程脚本拉起**
2. **torchrun / external launcher**
3. **在线多实例服务**

这三种方式的核心区别，不在模型怎么跑，而在：

- 谁负责拉起多个 DP rank
- 谁负责切请求
- 谁负责跨实例负载均衡

### 源码解析

**1. 离线多进程 DP：`examples/offline_inference/data_parallel.py`**

这个例子最直观的一点，是它直接用环境变量告诉每个进程自己的 DP 身份：

```python
os.environ["VLLM_DP_RANK"] = str(global_dp_rank)
os.environ["VLLM_DP_RANK_LOCAL"] = str(local_dp_rank)
os.environ["VLLM_DP_SIZE"] = str(dp_size)
os.environ["VLLM_DP_MASTER_IP"] = dp_master_ip
os.environ["VLLM_DP_MASTER_PORT"] = str(dp_master_port)
```

然后每个 rank 自己只处理自己那部分 prompts：

```python
prompts = prompts[start(global_dp_rank) : start(global_dp_rank + 1)]
```

所以这种方式下：

- 请求切分在脚本层完成
- vLLM 负责进程内和进程间执行

**2. torchrun / external launcher：`torchrun_dp_example.py`**

这个例子用了：

```python
LLM(
    ...,
    data_parallel_size=args.dp_size,
    distributed_executor_backend="external_launcher",
)
```

这里的关键点是 `external_launcher`。

因为在这种模式下，vLLM 不再自己生成一整套多进程树，而是假设：

- 外部已经把多个 rank 拉起来了
- vLLM 每个实例只接管自己的一个 worker / 一个 rank 视角

**3. 在线多实例 DP：`multi_instance_data_parallel.py`**

这个例子走的是 `AsyncLLMEngine`，并显式传了：

```python
engine_args = AsyncEngineArgs(
    data_parallel_size=2,
    data_parallel_address="127.0.0.1",
    data_parallel_rpc_port=62300,
    data_parallel_size_local=1,
)
```

然后请求生成时还可以指定目标 DP rank：

```python
engine_client.generate(..., data_parallel_rank=1)
```

这说明在线 DP 场景下，请求路由已经不只是本地脚本切分，而是可以显式选择或由负载均衡器决定。

### 代码示例

**例 1：离线多进程 DP**

```bash
python vllm/examples/offline_inference/data_parallel.py \
  --model ibm-research/PowerMoE-3b \
  --dp-size 2 \
  --tp-size 1
```

**例 2：torchrun + external launcher**

```bash
torchrun --nproc-per-node=2 \
  vllm/examples/offline_inference/torchrun_dp_example.py \
  --dp-size 2 \
  --tp-size 1
```

**例 3：在线多实例 DP**

```bash
python vllm/examples/online_serving/multi_instance_data_parallel.py
```

这些例子分别对应：

- 自己拉多进程
- 外部 launcher 拉多进程
- 在线服务多实例协同

## 12.4 混合张量并行和数据并行

### 原理讲解

实际部署里，DP 很少单独使用，最常见的是和 TP 组合。

原因很简单：

- 只用 DP：单个副本仍然要完整放下模型
- 只用 TP：单副本显存压力下降了，但吞吐扩展有限
- **TP + DP**：既能让单副本跨多卡放下模型，也能通过多副本吃掉更多并发

所以混合并行里最核心的一个公式是：

**总卡数 = DP x TP x PP x 其他并行维度**

### 源码解析

`ParallelConfig` 里已经把这件事写成了两个层次：

```python
self.world_size = (
    self.pipeline_parallel_size
    * self.tensor_parallel_size
    * self.prefill_context_parallel_size
)

@property
def world_size_across_dp(self) -> int:
    return self.world_size * self.data_parallel_size
```

也就是说：

- `world_size`：一个 DP 副本内部需要多少 rank
- `world_size_across_dp`：所有 DP 副本加起来一共多少 rank

再看 `initialize_model_parallel()` 里的 rank 布局：

```python
# the layout order is: ExternalDP x DP x PP x TP
all_ranks = torch.arange(world_size).reshape(
    -1,
    data_parallel_size,
    pipeline_model_parallel_size,
    prefill_context_model_parallel_size,
    tensor_model_parallel_size,
)
```

这意味着当 `DP=2, TP=2` 时，你可以把全局 rank 理解成：

- 第一个 DP 副本内部有一组 TP ranks
- 第二个 DP 副本内部也有一组 TP ranks

每个 DP 副本内部继续按 TP 规则协作。

### 代码示例

下面给一个 `DP=2, TP=2` 的 rank 划分示意：

```python
global_ranks = [0, 1, 2, 3]

dp0 = [0, 1]  # 第 0 个数据并行副本内部的 TP 组
dp1 = [2, 3]  # 第 1 个数据并行副本内部的 TP 组

print("DP rank 0 uses TP ranks:", dp0)
print("DP rank 1 uses TP ranks:", dp1)
```

可以把它画成：

```text
DP0: [TP0, TP1]
DP1: [TP0, TP1]
```

注意这里第二行里的 `TP0/TP1` 是“组内角色”，不是全局 rank 编号。

### 架构总览

```text
            TP + DP 混合并行的直觉图
========================================================================

全局 ranks: 0  1  2  3  4  5  6  7

假设:
  DP = 2
  TP = 2
  PP = 2

则可以理解为:

DP rank 0:
  PP stage 0 -> TP ranks [0, 1]
  PP stage 1 -> TP ranks [2, 3]

DP rank 1:
  PP stage 0 -> TP ranks [4, 5]
  PP stage 1 -> TP ranks [6, 7]
```

这个图最核心的意思是：

- DP 复制的是“整条 TP/PP 子拓扑”
- 不是简单复制单张卡

## 总结

1. 推理场景下的 DP 本质是多副本分流请求，主要扩吞吐，而不是像 TP 那样直接帮单请求省显存
2. `ParallelConfig` 是 DP 的配置总入口，`parallel_state.py` 是 DP 真正落地的分布式状态中心
3. `init_distributed_environment()` 会把 DP 维度并进全局 world，`initialize_model_parallel()` 会进一步切出 DP/TP/PP 等 group
4. 推理 DP 的跨 rank 同步重点是轻量控制信息，比如 token 数、cudagraph size、全局运行状态，而不是训练里的梯度同步
5. vLLM 同时支持离线多进程 DP、torchrun/external launcher，以及在线多实例 DP
6. 混合并行时最重要的理解是：DP 复制的是一整个 TP/PP 子拓扑，`world_size_across_dp = world_size x data_parallel_size`

## 思考题

1. 为什么说推理场景下 DP 主要提升的是吞吐，而不是单请求延迟？
2. 在 `DP=2, TP=2` 的场景里，如果只增加 DP 而不增加 TP，会对模型放置和吞吐分别产生什么影响？
3. `parallel_state.py` 为什么要先构造一个 `all_ranks` 的高维张量再去切组，而不是手写很多 rank 列表？
4. 离线多进程 DP、external launcher、在线多实例 DP 这三种方式的最大差别分别是什么？
5. `dp_utils.py` 为什么同步的是 `num_tokens` 和 `cudagraph_size` 这种轻量元信息？如果完全不做这类同步，会在哪些路径上出问题？
