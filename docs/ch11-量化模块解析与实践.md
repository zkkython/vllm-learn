> **关键源码文件**：
> - `vllm/vllm/model_executor/layers/quantization/__init__.py` -- 量化方法注册与分发
> - `vllm/vllm/model_executor/model_loader/weight_utils.py` -- `get_quant_config()`，负责读取量化配置
> - `vllm/vllm/model_executor/model_loader/utils.py` -- `configure_quant_config()` 与 `process_weights_after_loading()`

1. 理解 vLLM 支持的量化方式，不只是“有哪些名字”，还包括它们的配置来源和接入方式
2. 掌握离线量化 checkpoint、在线量化、量化 + LoRA 三类常见使用路径
3. 理解 `get_quant_config() -> configure_quant_config() -> get_quant_method() -> create_weights() -> process_weights_after_loading()` 的源码主链
4. 掌握量化方法是如何真正挂到 `LinearBase` 和其他层上的
5. 能够从 vLLM 源码角度解释“为什么有些量化是在 load 阶段做，有些是在 process_weights_after_loading 阶段做”

## 11.1 vLLM 量化功能总结

### 原理讲解

从使用者角度看，vLLM 的量化功能至少覆盖了三类需求：

1. **直接加载离线量化 checkpoint**
2. **加载高精度 checkpoint 后做在线量化**
3. **量化模型继续叠加 LoRA、RLHF 重载等能力**

所以第11章的重点不是重复量化原理，而是回答：

**vLLM 到底是怎么把这么多量化方法接进统一框架里的？**

### 源码解析

**1. vLLM 支持的量化方法集中在 `quantization/__init__.py`**

```python
QuantizationMethods = Literal[
    "awq", "fp8", "fp_quant", "gptq", "bitsandbytes",
    "torchao", "rtn", "inc", ...
]
```

这意味着上层只要传 `quantization="awq"` 或 `quantization="torchao"` 这样的名字，就能走到统一分发逻辑。

**2. 真正的量化类分发在 `get_quantization_config()`**

```python
def get_quantization_config(quantization: str) -> type[QuantizationConfig]:
    ...
    method_to_config = {
        "awq": AWQConfig,
        "fp8": Fp8Config,
        "torchao": TorchAOConfig,
        ...
    }
```

所以 vLLM 的量化入口不是“一个大 if-else + 直接调 kernel”，而是先把字符串方法名变成对应的配置类。

**3. 再由 `weight_utils.get_quant_config()` 决定配置来源**

```python
quant_cls = get_quantization_config(model_config.quantization)
hf_quant_config = getattr(model_config.hf_config, "quantization_config", None)
...
return quant_cls.from_config(config)
```

这个函数很重要，因为它回答了一个常见问题：

**量化配置到底从哪里来？**

答案可能有三种：

- HuggingFace config 里的 `quantization_config`
- `hf_overrides` 里传入的 json / config file
- 模型目录中的量化 json 文件

### 代码示例

下面用最小例子概括“字符串方法名 -> 配置类”的过程：

```python
class AWQConfig:
    pass


class TorchAOConfig:
    pass


METHOD_TO_CONFIG = {
    "awq": AWQConfig,
    "torchao": TorchAOConfig,
}


def get_quant_config_cls(name):
    return METHOD_TO_CONFIG[name]


print(get_quant_config_cls("awq"))
print(get_quant_config_cls("torchao"))
```

## 11.2 vLLM 量化推理实践

### 原理讲解

vLLM 里的量化实践，最常见可以分成两条主线：

1. **离线量化 checkpoint 直接推理**
2. **在线量化 / 训练后重载**

如果你只是部署一个已经量化好的模型，第一条足够。
如果你要做 RLHF、持续更新权重或试验 torchao 配置，第二条就很重要。

### 源码解析

**1. 离线量化 + LoRA 的示例**

`examples/offline_inference/lora_with_quantization_inference.py` 里给了几个典型组合：

```python
engine_args = EngineArgs(
    model=model,
    quantization=quantization,
    enable_lora=True,
    max_lora_rank=64,
    max_loras=4,
)
```

而测试配置里直接用了：

```python
{
    "model": "TheBloke/TinyLlama-1.1B-Chat-v0.3-AWQ",
    "quantization": "awq",
    "lora_repo": "jashing/tinyllama-colorist-lora",
}
```

这说明对用户来说，离线量化最直接的使用方式就是：

- 模型本身就是 AWQ / GPTQ / bitsandbytes 之类的量化 checkpoint
- 上层显式传 `quantization="..."` 即可

**2. 在线量化的示例**

`examples/offline_inference/rlhf_online_quant.py` 展示了 TorchAO 的在线量化用法：

```python
config = Float8DynamicActivationFloat8WeightConfig(granularity=PerRow())
json_str = json.dumps(config_to_dict(config))

llm = MyLLM(
    model="facebook/opt-125m",
    hf_overrides={"quantization_config_dict_json": json_str},
    ...
)
```

这里最关键的是：

- checkpoint 本身不一定已经量化
- 但可以通过 `hf_overrides` 把量化配置动态注入 vLLM

这正是在线量化路径的一个典型入口。

### 代码示例

**例 1：离线 AWQ 推理**

```python
from vllm import LLM, SamplingParams


llm = LLM(
    model="TheBloke/TinyLlama-1.1B-Chat-v0.3-AWQ",
    quantization="awq",
)

outputs = llm.generate(
    ["Hello, my name is"],
    SamplingParams(temperature=0.0, max_tokens=32),
)
print(outputs[0].outputs[0].text)
```

**例 2：在线 TorchAO 配置注入**

```python
import json
from vllm import LLM


torchao_cfg = {
    "quant_type": {
        "default": {
            "_type": "Float8DynamicActivationFloat8WeightConfig"
        }
    }
}

llm = LLM(
    model="facebook/opt-125m",
    quantization="torchao",
    hf_overrides={"quantization_config_dict_json": json.dumps(torchao_cfg["quant_type"]["default"])},
)
```

这里的第二个例子是教学版，真实场景里通常会从 torchao config 对象序列化得到这个 json。

## 11.3 vLLM 的量化模块源码解析

### 原理讲解

vLLM 量化模块最值得掌握的一点，是它不是在某个地方“一次性把模型量化完”。

它更像一条流水线：

1. 先决定当前量化配置是什么
2. 模型初始化时，把量化方法挂到每个层上
3. 层在创建权重时使用量化权重格式
4. 权重加载后，再做 repack / online quantize / 后处理

如果把这条链看清楚，后面读任何具体量化方法都会容易很多。

### 源码解析

这条主线可以拆成 5 步。

**1. 读取量化配置**

```python
# vllm/vllm/model_executor/model_loader/weight_utils.py
quant_cls = get_quantization_config(model_config.quantization)
...
return quant_cls.from_config(config)
```

这一步的输出是一个 `QuantizationConfig` 对象，而不是直接的 kernel。

**2. 模型初始化前，把量化配置和模型类绑定起来**

```python
# vllm/vllm/model_executor/model_loader/utils.py
if vllm_config.quant_config is not None:
    configure_quant_config(vllm_config.quant_config, model_class)
```

`configure_quant_config()` 会把模型类里的：

- `packed_modules_mapping`
- `hf_to_vllm_mapper`

这些信息传给 quant config。这样量化配置才能正确识别 fused module 和名字映射。

**3. 每个线性层初始化时决定自己的 `quant_method`**

```python
# vllm/vllm/model_executor/layers/linear.py :: LinearBase.__init__
if quant_config is None:
    self.quant_method = UnquantizedLinearMethod()
else:
    self.quant_method = quant_config.get_quant_method(self, prefix=prefix)
```

这一步非常关键，因为它意味着：

- 同一个模型里，不同层可以拿到不同量化方法
- 某些层甚至可以被跳过，回退成 `UnquantizedLinearMethod`

**4. 层创建权重时，实际创建的是量化权重格式**

```python
# vllm/vllm/model_executor/layers/linear.py :: ColumnParallelLinear.__init__
self.quant_method.create_weights(...)
```

如果这里的 `quant_method` 是 `AWQLinearMethod`，它创建的就不是普通 `weight`，而是：

- `qweight`
- `qzeros`
- `scales`

如果是 `TorchAOLinearMethod`，创建的则还是 `weight`，但后面可能会在线转换成 tensor subclass / packed tensor。

**5. 权重加载后再做后处理**

```python
# vllm/vllm/model_executor/model_loader/utils.py
for _, module in model.named_modules():
    quant_method = getattr(module, "quant_method", None)
    if isinstance(quant_method, QuantizeMethodBase):
        quant_method.process_weights_after_loading(module)
```

为什么要有这一步？

因为很多量化方法在“读完 checkpoint”之后还要再做一次工程化处理，比如：

- repack
- 生成 scale
- 在线量化
- 转成更适合 kernel 的 packed tensor

**6. TorchAO 在线量化就是典型例子**

在 `TorchAOLinearMethod.process_weights_after_loading()` 里：

```python
weight = torchao_quantize_param_data(
    layer.weight, self.quant_config.torchao_config
)
weight = torch.nn.Parameter(
    convert_to_packed_tensor_based_on_current_hardware(weight),
    weight.requires_grad,
)
layer.register_parameter("weight", weight)
```

这说明 torchao 路线在很多情况下不是“checkpoint 里已经是量化格式”，而是：

**先加载普通权重，再在 post-load 阶段转成量化表示。**

`online_quantization.py` 则进一步处理了“已经量化过的模型如何从高精度权重重载”的问题，用于 RLHF 等场景。

### 代码示例

下面用一个最小版本把这条链串起来：

```python
class QuantConfig:
    def get_quant_method(self, layer, prefix):
        return QuantMethod()


class QuantMethod:
    def create_weights(self, layer):
        layer.qweight = "packed_weight"

    def process_weights_after_loading(self, layer):
        layer.ready = True


class LinearLayer:
    def __init__(self, quant_config):
        self.quant_method = quant_config.get_quant_method(self, "layer.0")
        self.quant_method.create_weights(self)


layer = LinearLayer(QuantConfig())
layer.quant_method.process_weights_after_loading(layer)
print(layer.qweight, layer.ready)
```

```text

========================================================================

   |

   |
```

## 总结

1. vLLM 的量化能力不是单个 feature，而是一整套从配置读取、层方法绑定到权重后处理的统一框架
2. `get_quantization_config()` 决定“用哪个量化类”，`get_quant_config()` 决定“配置从哪里读”
3. 量化方法真正挂到层上的关键点在 `LinearBase.__init__` 里的 `get_quant_method()`
4. `create_weights()` 决定层里长出什么权重格式，`apply()` 决定 forward 怎么执行，`process_weights_after_loading()` 决定加载后怎么收尾
5. 离线量化 checkpoint 和在线量化最大的区别，不在上层 API 名字，而在“量化动作发生在哪个阶段”
6. TorchAO 和在线量化路径特别值得单独理解，因为它们会涉及“高精度权重重载 -> 再量化”的额外流程

## 思考题

1. 为什么 vLLM 要把“量化配置”和“量化方法”拆成 `QuantizationConfig` 与 `QuantizeMethodBase` 两层，而不是一个类全包？
2. `LinearBase.__init__` 里调用 `quant_config.get_quant_method()` 的设计，有什么好处？如果改成模型加载后统一替换层，会遇到什么问题？
3. 为什么很多量化方法要等到 `process_weights_after_loading()` 才做真正的 repack 或在线量化，而不是在 `create_weights()` 时一步到位？
4. 离线量化 checkpoint 和在线量化在“权重重载”场景下，谁更复杂？复杂点主要体现在哪？
5. 如果你要排查“量化模型加载后结果不对”，你会优先检查 `get_quant_config()`、`get_quant_method()` 还是 `process_weights_after_loading()`？为什么？
