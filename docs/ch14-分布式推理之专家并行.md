## 14.1 MoE 概述

### 原理讲解

MoE（Mixture of Experts）层和普通 MLP 最大的不同是：

- 普通 MLP：所有 token 走同一组参数
- MoE：每个 token 只走 top-k 个专家

所以 MoE 的核心流程是：

1. Router 根据 `router_logits` 给每个 token 选 top-k 专家
2. 把 token 发给对应专家
3. 各专家执行自己的前向
4. 按 router 权重把多个专家输出加权合并

这件事为什么特别适合专家并行（EP）？

因为专家天然就是一组“可分发对象”：

- 不同 GPU 可以持有不同专家权重
- token 根据路由结果发往专家所在 GPU
- 算完再把结果合回来

和 TP 相比，EP 切的不是一个大矩阵的维度，而是：

**直接切“专家集合”。**

### 源码解析

**1. `FusedMoE` 是 vLLM 中 MoE 层的核心实现**

`FusedMoE` 的类注释写得很直白：

- 它内部既包含 `MergedColumnParallel` 风格的 `w13`
- 也包含 `RowParallelLinear` 风格的 `w2`

也就是说，一个专家本质上仍然是两层线性：

```text
hidden_states
   -> w1 / w3
   -> activation
   -> w2
```

只是现在这套权重有很多份，而且每个 token 只会进入少数几份。

**2. 专家是否启用 EP，取决于 `FusedMoEParallelConfig`**

在 `FusedMoE.__init__()` 中：

```python
self.moe_parallel_config = FusedMoEParallelConfig.make(...)
```

随后通过：

```python
self.use_ep
self.ep_size
self.ep_rank
```

来判断当前层是否真的处于专家并行模式。

**3. `determine_expert_map()` 决定“哪些专家归当前 rank 管”**

```python
local_num_experts, expert_map, expert_mask = determine_expert_map(
    ep_size=self.ep_size,
    ep_rank=self.ep_rank,
    global_num_experts=self.global_num_experts,
    expert_placement_strategy=self.expert_placement_strategy,
)
```

这个函数的输出非常关键：

- `local_num_experts`：当前 rank 持有多少个专家
- `expert_map`：全局专家 id 到本地专家 id 的映射
- `expert_mask`：某些后端用于 kernel 过滤的专家掩码

如果是线性放置策略：

- rank0 可能拿 `[0, 1, 2]`
- rank1 可能拿 `[3, 4, 5]`

如果是 round-robin：

- rank0 可能拿 `[0, 2, 4]`
- rank1 可能拿 `[1, 3, 5]`

### 代码示例

下面用一个最小例子说明专家并行切分的本质：

```python
global_experts = [0, 1, 2, 3]
ep_size = 2

rank0_experts = global_experts[0:2]
rank1_experts = global_experts[2:4]

token_routes = {
    "t0": [0],
    "t1": [3],
    "t2": [1],
}

print("rank0 experts:", rank0_experts)
print("rank1 experts:", rank1_experts)
print("token routes:", token_routes)
```

这里的关键不是“专家数变多了”，而是：

**token 必须被送到正确的专家所在 rank。**

### 架构总览

```text
                 MoE + EP 的基本结构
========================================================================

router_logits
   |
   v
top-k expert ids
   |
   v
dispatch tokens to expert owner ranks
   |
   v
local experts execute:
   w13 -> activation -> w2
   |
   v
combine outputs by top-k weights
```

## 14.2 AlltoAll 通信原理

### 原理讲解

专家并行最核心的通信，不是 `AllReduce`，而是 `AlltoAll`。

原因很简单：

- TP 更像“大家一起算同一个层”
- EP 更像“大家各自持有不同专家，token 要按目的地分发”

所以 EP 的通信模式是：

- rank0 把一部分 token 发给 rank1
- rank1 也把自己的另一部分 token 发给 rank0
- 每个 rank 发出去和收进来的内容都不一样

这就是 `AlltoAll` 最适合的场景。

### 源码解析

**1. `All2AllManager` 把通信抽象成 `dispatch()` 和 `combine()`**

在 `all2all.py` 里，不同后端都围绕同一组接口展开：

```python
dispatch(hidden_states, router_logits, ...)
combine(hidden_states, ...)
```

因此从 `FusedMoE` 的角度看，不需要关心底层具体是：

- naive broadcast
- allgather + reducescatter
- PPLX kernels
- DeepEP kernels

只需要调用统一接口。

**2. `NaiveAll2AllManager` 是最直观的实现**

`NaiveAll2AllManager` 的思路比较“朴素”：

- `dispatch()` 通过广播 / 复制，把 token 发到所有相关 rank
- `combine()` 通过 `all_reduce` 把输出汇总，再切回本 rank 结果

这很好理解，但不一定最高效。

**3. `AgRsAll2AllManager` 用 `all_gatherv + reduce_scatterv` 组织通信**

这一类后端的思路是：

- dispatch 阶段把各 rank token 按需要 gather 起来
- combine 阶段再用 reduce-scatter 把结果按 rank 切回去

它仍然完成的是 “token 去专家、结果回 token” 这件事，只是通信组织方式更工程化。

**4. `DeepEP / PPLX` 后端进一步把 prepare / dispatch / combine kernel 化**

例如 `DeepEPHTAll2AllManager`、`DeepEPLLAll2AllManager` 和 `PPLXAll2AllManager`：

- 会创建专门的 handle / buffer
- 使用更底层、更贴近硬件的 kernel
- 尽量减少中间搬运和 Python 侧开销

### 代码示例

下面用一个小例子理解 `AlltoAll`：

```python
rank0_tokens = ["t0->expert0", "t1->expert3"]
rank1_tokens = ["t2->expert1", "t3->expert2"]

# 假设 expert0/1 在 rank0, expert2/3 在 rank1
after_dispatch_rank0 = ["t0->expert0", "t2->expert1"]
after_dispatch_rank1 = ["t1->expert3", "t3->expert2"]

print("rank0 after dispatch:", after_dispatch_rank0)
print("rank1 after dispatch:", after_dispatch_rank1)
```

这里最值得记住的是：

**通信前按“token 所在 rank”组织，通信后按“专家所在 rank”组织。**

### 数据流图

```text
                    AlltoAll 的直观含义
========================================================================

dispatch 前:
rank0: token0 token1
rank1: token2 token3

按 expert owner 重新分桶后:
rank0 <- token0 token2
rank1 <- token1 token3

本地专家计算完成后:
rank0: partial outputs of token0 token2
rank1: partial outputs of token1 token3

combine 后:
回到按原 token 语义组织的输出
```

## 14.3 vLLM EP 之 MoE 层架构和推理流程解析

### 原理讲解

在 vLLM 里，EP 不是一个“挂在模型外面的大开关”，而是：

**具体落在 `FusedMoE` 这一层里。**

因此理解 EP，最重要的不是先看 engine，而是先看：

- `FusedMoE.__init__()`
- `FusedMoE.forward_impl()`

这两处几乎把专家并行的骨架都搭出来了。

### 源码解析

**1. `FusedMoE.__init__()` 会先决定当前层的并行形态**

```python
self.moe_parallel_config = FusedMoEParallelConfig.make(...)
self.global_num_experts = num_experts + num_redundant_experts
self.logical_num_experts = num_experts
```

这里已经能看出两个重要概念：

- `logical_num_experts`：模型逻辑上的专家数
- `global_num_experts`：物理上真正存在的专家数，可能包含冗余专家

这为第15章的 EPLB 做了铺垫。

**2. EP 下会初始化 `_expert_map`，把全局专家映射到本地专家**

```python
local_num_experts, expert_map, expert_mask = determine_expert_map(...)
self.local_num_experts = local_num_experts
self.register_buffer("_expert_map", expert_map)
```

这意味着本 rank 在 forward 时不直接处理“全局专家空间”，而是：

- 先根据路由得到全局专家 id
- 再映射到本地专家 id

**3. `maybe_init_modular_kernel()` 会按后端切换 prepare / finalize 实现**

```python
prepare_finalize = self.quant_method.maybe_make_prepare_finalize(...)
self.quant_method = FusedMoEModularMethod.make(
    self, self.quant_method, prepare_finalize, self.shared_experts
)
```

这一步很关键，因为它说明：

- 不同 EP 后端不只是“换个通信 API”
- 它们可能直接改变整条 MoE kernel 的执行形态

例如：

- 有的后端把 dispatch 和 combine 放到 prepare / finalize 阶段
- 有的后端把 top-k 权重应用和 reduce 也融合掉

**4. `all2all_utils.maybe_make_prepare_finalize()` 负责挑选具体实现**

这个函数会根据当前 `moe_parallel_config` 和 `all2all_backend`，构造：

- `PplxPrepareAndFinalize`
- `DeepEPHTPrepareAndFinalize`
- `DeepEPLLPrepareAndFinalize`

如果没有启用 all2all kernels，就返回 `None`。

也就是说，`FusedMoE` 的 forward 路径不是单一路径，而是：

**根据通信后端动态选中的。**

### 代码示例

下面给出一个最小的 EP 配置示意：

```python
parallel_config = {
    "tensor_parallel_size": 1,
    "data_parallel_size": 1,
    "enable_expert_parallel": True,
    "all2all_backend": "deepep_high_throughput",
}

print(parallel_config)
```

在这个配置下：

- 普通 dense 层仍然按 TP/单卡逻辑执行
- 只有 MoE 层会走 EP 分片和 AlltoAll 路径

### 流程图

```text
                 FusedMoE 在 EP 模式下的初始化
============================================================================

FusedMoE.__init__()
   |
   +--> FusedMoEParallelConfig.make()
   |
   +--> determine_expert_map()
   |      - local_num_experts
   |      - expert_map
   |
   +--> quant_method.create_weights()
   |
   +--> maybe_init_modular_kernel()
          - 根据 pplx / deepep / naive 等后端选择 prepare_finalize
```

## 14.4 vLLM EP 之 Dispatch-Compute-Combine 推理流程解析

### 原理讲解

EP MoE 的 forward，可以粗暴概括成三步：

1. **Dispatch**：把 token 发给专家 owner rank
2. **Compute**：本地专家执行 `w13 -> activation -> w2`
3. **Combine**：把专家输出按 top-k 权重聚合，再还原回 token 顺序

但在 vLLM 里，这三步不是总以同一种形式出现。

有两类典型路径：

1. **朴素路径**：`dispatch()` / `combine()` 显式写在 `FusedMoE.forward_impl()` 里
2. **融合路径**：dispatch / combine 融入 modular kernel 的 prepare / finalize

### 源码解析

**1. `select_experts()` 先做路由**

```python
topk_weights, topk_ids, token_expert_indices = fused_topk(...)
```

对于 grouped top-k 或特定模型，还可能走：

- `grouped_topk`
- `fused_topk_bias`
- 自定义 routing function

路由完成后，如果开启 EPLB，还会有一个很关键的改写：

```python
topk_ids = eplb_map_to_physical_and_record(
    topk_ids=topk_ids,
    expert_load_view=self.expert_load_view,
    logical_to_physical_map=self.logical_to_physical_map,
    logical_replica_count=self.logical_replica_count,
)
```

也就是说：

- Router 原始选出来的是逻辑专家
- 真正执行前，可能会被改写成物理专家

**2. 朴素路径下，`forward_impl()` 显式调用 `dispatch()`**

```python
do_naive_dispatch_combine = self.dp_size > 1 and not isinstance(
    self.quant_method, FusedMoEModularMethod
)

if do_naive_dispatch_combine:
    hidden_states_combined, router_logits = get_ep_group().dispatch(
        hidden_states, router_logits, self.is_sequence_parallel
    )
```

这一步之后：

- `hidden_states` 的组织方式已经变了
- 当前 rank 拿到的是“应该由本 rank 专家处理的 token”

**3. 专家计算由 `quant_method.apply()` 触发**

```python
final_hidden_states = self.quant_method.apply(
    layer=self,
    x=hidden_states_combined if do_naive_dispatch_combine else hidden_states,
    router_logits=router_logits,
)
```

不管底层是普通 fused kernel 还是 modular kernel，这一层都承担：

- 调用 top-k 相关信息
- 组织专家 GEMM
- 生成未 reduce / 已 reduce 的专家输出

**4. combine 阶段把结果还原回 token 视角**

```python
if do_naive_dispatch_combine:
    states = get_ep_group().combine(states, self.is_sequence_parallel)
```

如果还启用了 PCP：

```python
states = get_pcp_group().reduce_scatter(states, dim=0)
```

因此最终输出不仅要从专家视角回到 token 视角，还可能继续经过上下文并行的切分收敛。

### 代码示例

下面用一个极简版本模拟 dispatch-compute-combine：

```python
tokens = {
    "t0": "expert0",
    "t1": "expert3",
    "t2": "expert1",
}

owner = {
    "expert0": "rank0",
    "expert1": "rank0",
    "expert3": "rank1",
}

dispatch_bucket = {"rank0": [], "rank1": []}
for token, expert in tokens.items():
    dispatch_bucket[owner[expert]].append((token, expert))

local_outputs = {
    "rank0": {"t0": 1.2, "t2": 2.3},
    "rank1": {"t1": 9.9},
}

combined = {"t0": 1.2, "t1": 9.9, "t2": 2.3}
print(dispatch_bucket)
print(combined)
```

### 数据流图

```text
                EP forward 的主链路
========================================================================

hidden_states + router_logits
   |
   v
select_experts()
   |
   +--> fused_topk / grouped_topk
   +--> (可选) eplb_map_to_physical_and_record
   |
   v
dispatch
   |
   +--> naive dispatch / DeepEP / PPLX prepare
   |
   v
expert compute
   |
   +--> w13
   +--> activation
   +--> w2
   |
   v
combine
   |
   +--> top-k weight apply
   +--> reduce / unpermute
   +--> token 顺序恢复
```

## 14.5 vLLM EP 之专家计算内核实现分析

### 原理讲解

如果只从算法上看，专家计算很简单：

```text
expert_out = w2( act( w13(x) ) )
```

但在工程实现上，真正困难的是：

1. token 会被路由到不同专家
2. 每个专家的 token 数不一样
3. top-k 还要加权求和
4. 需要兼顾量化、chunking、不同后端和显存复用

所以 vLLM 把这部分做成了模块化结构。

### 源码解析

**1. `modular_kernel.py` 明确给出了 MoE 的模块化分解**

可以把它概括成：

```text
[Router] -> [Quantize-Dispatch] -> [Permute-Experts-Unpermute] -> [Combine]
```

对应抽象接口包括：

- `FusedMoEPrepareAndFinalize`
- `FusedMoEPermuteExpertsUnpermute`
- `TopKWeightAndReduce`

这让不同后端可以只替换自己那一段，而不用重写整条链。

**2. `MoEPrepareAndFinalizeNoEP` 展示了非 EP 场景下的最小 prepare / finalize**

```python
a1q, a1q_scale = moe_kernel_quantize_input(...)
weight_and_reduce_impl.apply(
    output=output,
    fused_expert_output=fused_expert_output,
    topk_weights=topk_weights,
    topk_ids=topk_ids,
    apply_router_weight_on_input=apply_router_weight_on_input,
)
```

它做了两件事：

- prepare：量化输入
- finalize：应用 top-k 权重并 reduce

**3. `TopKWeightAndReduceContiguous` 负责“专家输出加权求和”**

```python
if not apply_router_weight_on_input:
    fused_expert_output.mul_(topk_weights.view(m, -1, 1))

ops.moe_sum(fused_expert_output, output)
```

这里的逻辑很重要：

- 如果 router 权重没提前乘到输入上
- 那就在输出阶段再乘一次
- 然后用 `moe_sum` 在 top-k 维度上求和

这正是 “多个专家输出 -> 一个 token 最终输出” 的核心。

**4. `FusedMoEModularKernel` 负责 scratch space、chunking 和总装**

它会：

- 根据 `workspace_shapes()` 申请中间 buffer
- 决定是否按 chunk 处理 token
- 调用 `prepare_finalize` 与 `fused_experts.apply()`

这部分是工程实现里最容易被忽略但非常关键的一层，因为：

**MoE 性能很多时候不是卡在算子公式，而是卡在中间张量组织和显存复用。**

**5. `fused_moe.py` 里的 kernel 才是真正执行专家 GEMM 的地方**

例如 `fused_moe_kernel_gptq_awq()` 的参数里已经出现：

- `A`: token 输入
- `B`: stacked expert weights
- `sorted_token_ids`
- `expert_ids`

这说明 kernel 视角下的数据已经不再是“原始 token 顺序”，而是：

**按专家和 token 排序后的计算布局。**

### 代码示例

下面用伪代码表达专家计算的本质：

```python
def expert_forward(x, w13, w2):
    hidden = x @ w13
    hidden = silu(hidden[:, : hidden.shape[1] // 2]) * hidden[:, hidden.shape[1] // 2 :]
    out = hidden @ w2
    return out


def combine_topk(outputs, weights):
    total = 0
    for out, w in zip(outputs, weights):
        total += out * w
    return total
```

真实 vLLM 实现会把：

- token 重排
- 专家分桶
- 量化
- reduce

全部融合到更低层的 kernel 和 workspace 管理里。

### 完整流程图

```text
            vLLM 专家计算内核的模块化分层
============================================================================

select_experts()
   |
   v
prepare_finalize.prepare()
   |
   +--> 输入量化
   +--> 后端特定 dispatch 准备
   |
   v
fused_experts.apply()
   |
   +--> permute tokens by expert
   +--> w13 gemm
   +--> activation
   +--> w2 gemm
   |
   v
prepare_finalize.finalize()
   |
   +--> top-k 权重应用
   +--> reduce / unpermute
```

## 14.6 vLLM EP 之完整函数调用链总结

### 原理讲解

到这里，可以把 EP 的调用链压缩成一句话：

**ModelRunner 调模型，模型走到 `FusedMoE`，`FusedMoE` 在内部完成路由、通信、专家计算和结果回收。**

所以 EP 的复杂性主要不在 engine，而在：

- MoE 层内部的状态组织
- 通信后端的差异
- kernel 的模块化组合

### 源码解析

把一次完整调用链按顺序写出来，大致是：

```text
GPUModelRunner.execute_model()
  -> model(...)
    -> 某层 FusedMoE.forward_native()
      -> torch.ops.vllm.moe_forward(...)
        -> FusedMoE.forward_impl(...)
          -> select_experts()
          -> dispatch(可选)
          -> quant_method.apply(...)
          -> combine(可选)
          -> 返回 hidden_states
```

如果启用了 modular kernel，`quant_method.apply(...)` 内部还会继续展开成：

```text
prepare_finalize.prepare()
  -> fused_experts.apply()
  -> prepare_finalize.finalize()
```

所以你可以把它理解成两层嵌套：

1. `FusedMoE` 负责 MoE 层语义
2. modular kernel 负责具体 kernel 编排

### 代码示例

下面用伪代码把这条链压缩出来：

```python
def moe_layer_forward(hidden_states, router_logits):
    topk_weights, topk_ids = select_experts(hidden_states, router_logits)
    dispatched = dispatch(hidden_states, topk_ids)
    expert_out = fused_expert_compute(dispatched, topk_ids)
    final = combine(expert_out, topk_weights, topk_ids)
    return final
```

## 总结

1. 专家并行切的不是矩阵维度，而是专家集合，因此通信模式从 TP 的 `AllReduce` 转成了 EP 的 `AlltoAll`。
2. `FusedMoE` 是 vLLM 中 EP 的真正落点，它负责专家映射、路由、dispatch、专家计算和 combine。
3. `determine_expert_map()` 决定当前 rank 持有哪些专家，`select_experts()` 决定每个 token 去哪些专家。
4. `dispatch / combine` 可以显式出现在 `forward_impl()` 中，也可以被更底层的 modular kernel 后端融合掉。
5. `TopKWeightAndReduce` 与 `PrepareAndFinalize` 是理解 vLLM MoE 内核分层的两个关键抽象。
6. EP 的核心收益是把大量专家权重分散到多卡上，但代价是 token 路由和结果回收带来的复杂通信。
