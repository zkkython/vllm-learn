## 17.1 torch.compile 基础

### 原理讲解

先把 `torch.compile` 自己做的事情说清楚。

它通常可以粗略拆成三层：

1. **Dynamo**：截获 Python `forward`，构造 FX graph
2. **AOT / FX / Inductor**：对图做优化和代码生成
3. **Runtime Dispatch**：在后续调用中复用已经编译好的图

普通 PyTorch 用户最常见的用法是：

```python
compiled_model = torch.compile(model)
```

但对 vLLM 来说，这还不够。因为 vLLM 面临的不是一个固定 batch shape 的训练图，而是：

- decode batch size 经常变化
- attention / custom op / cudagraph 之间要协调
- 编译缓存需要跨进程、跨重启复用

所以 vLLM 并不是“直接把整张模型交给 `torch.compile` 就结束”，而是在它外面又包了一层更细的控制逻辑。

### 源码解析

`CompilationMode` 把当前仓库里的编译模式分成四档：

```python
class CompilationMode(enum.IntEnum):
    NONE = 0
    STOCK_TORCH_COMPILE = 1
    DYNAMO_TRACE_ONCE = 2
    VLLM_COMPILE = 3
```

这四种模式的差异非常清楚：

- `NONE`：完全 eager
- `STOCK_TORCH_COMPILE`：尽量沿用原生 `torch.compile`
- `DYNAMO_TRACE_ONCE`：只做一次 Dynamo trace，后续尽量不再重编译
- `VLLM_COMPILE`：启用 vLLM 自己的编译后端、切图、缓存和 pass 流水线

再看 `support_torch_compile` 装饰器：

```python
@support_torch_compile(...)
class SomeModule(nn.Module):
    ...
```

它做的第一件关键事是：

- 给模块 forward 标出动态维度
- 决定这个模块是否参与 vLLM 的编译体系

`decorators.py` 里对应的核心逻辑是：

```python
torch._dynamo.mark_dynamic(arg, dims)
```

或者在 unbacked dynamic shape 模式下：

```python
torch._dynamo.decorators.mark_unbacked(...)
```

这说明 vLLM 对 `torch.compile` 的第一层增强，不是“额外加速”，而是：

**先把动态 shape 问题描述清楚。**

### 代码示例

下面给出一个最小的 `torch.compile` 概念示意：

```python
import torch
import torch.nn as nn


class Toy(nn.Module):
    def forward(self, x):
        return x * 2 + 1


model = Toy()
compiled = torch.compile(model)
print(compiled(torch.tensor([1, 2, 3])))
```

而在 vLLM 里，这个“compile 一个 forward”的动作，会被扩展成：

- 动态维度标记
- guard 控制
- backend 定制
- graph split
- cache 管理

### 架构总览

```text
                  torch.compile 的基础工作流
========================================================================

Python forward
   |
   v
Dynamo trace
   |
   v
FX graph
   |
   v
backend / Inductor codegen
   |
   v
compiled callable
```

## 17.2 vLLM 编译架构和优化技术

### 原理讲解

vLLM 在 `torch.compile` 外面又搭了一层编译架构，原因主要有三点：

1. **需要控制 guard**
2. **需要控制缓存**
3. **需要把编译与 cudagraph / custom op / attention 切图整合起来**

这决定了 vLLM 的编译架构不是“一个 backend 函数”，而是一整套：

- 配置层
- 模块装饰层
- backend 管理层
- 编译缓存层
- runtime dispatch 层

### 源码解析

**1. `CompilationConfig` 是总控配置**

它包含几类最重要的开关：

- `mode`
- `backend`
- `custom_ops`
- `splitting_ops`
- `compile_sizes`
- `compile_ranges_split_points`
- `cudagraph_mode`
- `pass_config`

也就是说，编译不是一个单点开关，而是一组策略组合。

**2. `TorchCompileWithNoGuardsWrapper` 控制 guard 行为**

`wrapper.py` 的类注释写得很明确：

> 当不是 `STOCK_TORCH_COMPILE` 时，会尽量把 guards 都去掉。

关键代码是：

```python
if mode != CompilationMode.STOCK_TORCH_COMPILE:
    options["guard_filter_fn"] = lambda x: [False for _ in x]
```

这意味着在 vLLM 自定义编译模式下，它会主动降低 Dynamo guard 对 runtime 的限制，以避免频繁重编译。

同时，`_compilation_context()` 还会：

- 提高 dynamo cache limit
- patch 掉 `GLOBAL_STATE` guard
- patch 掉 `TORCH_FUNCTION_MODE_STACK` guard

这说明 vLLM 编译体系非常关注“guard 噪声”。

**3. `VllmBackend` 是 vLLM 编译体系的核心 backend**

在 `CompilationConfig.init_backend()` 中：

```python
if self.mode == CompilationMode.VLLM_COMPILE:
    return VllmBackend(vllm_config)
```

也就是说，`VLLM_COMPILE` 并不是把 backend 名称改成 `"inductor"` 这么简单，而是把整个 backend 替换成了 `VllmBackend`。

**4. `compiler_interface.py` 解决的是“脱离单次 Dynamo 上下文后，编译产物如何继续复用”**

这一层最容易被忽略，但实际上非常关键。

`compiler_interface.py` 里定义的 `AlwaysHitShapeEnv` 和 `InductorAdaptor / InductorStandaloneAdaptor`，本质上是在解决一个很现实的问题：

- vLLM 需要多次、分段地触发 Inductor 编译
- 这些编译不一定都发生在同一个 Dynamo trace 生命周期里

所以它需要一个“更像独立编译器接口”的抽象层，而不只是把所有事情都塞回一次性的 Dynamo context。

**5. `CompilerManager` 负责缓存与编译产物管理**

它维护：

```python
self.cache: dict[tuple[Range, int, str], Any]
```

缓存 key 里包含：

- `Range`
- `graph_index`
- `compiler.name`

这说明 vLLM 的缓存不是“某个模型一个 compiled graph”，而是：

**按 compile range 和子图粒度缓存。**

**6. `PassConfig` 提供了 vLLM 自定义优化钩子**

例如：

- `fuse_norm_quant`
- `fuse_act_quant`
- `fuse_attn_quant`
- `fuse_gemm_comms`
- `enable_qk_norm_rope_fusion`

这类优化不是普通 `torch.compile` 默认就会替你做的，而是 vLLM 针对推理场景额外加上的。

### 代码示例

下面给出一个最小的 vLLM 编译配置示意：

```python
compilation_config = {
    "mode": "VLLM_COMPILE",
    "backend": "inductor",
    "cudagraph_mode": "FULL_AND_PIECEWISE",
    "pass_config": {
        "fuse_norm_quant": True,
        "fuse_act_quant": True,
    },
}

print(compilation_config)
```

### 数据流图

```text
                vLLM 编译架构的核心分层
========================================================================

CompilationConfig
   |
   +--> support_torch_compile
   +--> TorchCompileWithNoGuardsWrapper
   +--> VllmBackend
   +--> CompilerManager
   +--> PiecewiseBackend / CUDAGraphWrapper
```

## 17.3 分段编译 (Piecewise Compilation) 技术概述

### 原理讲解

为什么 vLLM 要搞 piecewise compilation？

因为在真实推理图里，并不是所有部分都同样适合：

- 一起编译
- 一起进入 cudagraph

最典型的例子就是 attention、自定义通信 op、某些 cudagraph 不兼容算子。

如果把整张图强行当成一个整体：

- 编译范围太大
- 一处不兼容会拖累全图
- runtime shape 的灵活性也会变差

所以 vLLM 的思路是：

**把图按特定 op 切开，只把合适的子图拿去编译/捕获。**

### 源码解析

**1. `splitting_ops` 决定在哪些 op 处切图**

`CompilationConfig` 里：

```python
splitting_ops: list[str] | None = None
```

默认情况下，如果是 v1 + piecewise cudagraph，vLLM 会把 attention 相关 op 当成切分边界。

它的类内 `_attention_ops` 默认列表就包括：

- `vllm::unified_attention`
- `vllm::unified_mla_attention`
- `vllm::mamba_mixer`
- `vllm::linear_attention`
等

**2. `split_graph()` 在 FX 层真正把图切开**

`backends.py` 里的 `split_graph()` 会遍历 graph node：

```python
if should_split(node, splitting_ops):
    subgraph_id += 1
    ...
```

然后调用：

```python
torch.fx.passes.split_module.split_module(...)
```

把一张 graph 变成多个 submodule。

**3. `PiecewiseCompileInterpreter` 会把可编译子图换成 `PiecewiseBackend`**

在解释 split 后的 graph 时：

```python
piecewise_backend = PiecewiseBackend(
    submod,
    self.vllm_config,
    index,
    len(self.compile_submod_names),
    sym_shape_indices,
    self.vllm_backend,
)
```

这说明 piecewise compilation 的单位不是整张模型，而是：

**切出来的每个可编译子图。**

**4. `PiecewiseBackend` 进一步按 runtime shape 做分派**

`PiecewiseBackend` 维护的是一组 `RangeEntry`：

```python
range_entries: dict[Range, RangeEntry]
```

运行时它会：

```python
runtime_shape = args[self.sym_shape_indices[0]]
range_entry = self._find_range_for_shape(runtime_shape)
```

也就是说，同一个子图还会再按：

- compile size
- compile range

决定用哪一份编译产物。

**5. compile size 还会受到 speculative decoding 的约束**

`CompilationConfig.adjust_cudagraph_sizes_for_spec_decode()` 会在 speculative decode 打开时，调整 cudagraph capture size：

- 至少要按 `num_speculative_tokens + 1` 的粒度对齐
- 如果同时开了 sequence parallel，还要再考虑 TP 粒度

这背后的原因很直接：

**speculative decoding 一次 forward 并不是只验证 1 个 token，而是“目标 token + 若干 draft token”一起进图。**

所以 compile size / cudagraph size 不能只按普通 decode 的 token 数理解。

### 代码示例

下面用一个最小例子说明 piecewise compilation 的想法：

```python
full_graph = ["embed", "attention", "mlp", "attention", "lm_head"]

split_points = ["attention"]
piecewise_graphs = [
    ["embed"],
    ["attention"],
    ["mlp"],
    ["attention"],
    ["lm_head"],
]

print(full_graph)
print(piecewise_graphs)
```

真实 vLLM 并不是把 attention “单独拿去编译”，而是用它作为切分边界，把前后更适合 cudagraph / compile 的子图组织起来。

### 流程图

```text
                  Piecewise Compilation 思路
========================================================================

full FX graph
   |
   v
split_graph(splitting_ops)
   |
   +--> submod_0
   +--> submod_1
   +--> submod_2
   ...
   |
   v
PiecewiseBackend
   |
   +--> compile for concrete sizes
   +--> compile for shape ranges
   |
   v
runtime dispatch by shape
```

## 17.4 vLLM 的编译流程

### 原理讲解

把当前仓库里的 vLLM 编译流程从头到尾串起来，大致可以分成五步：

1. 模块声明自己支持编译
2. 首次运行时标记动态 shape 并进入 `torch.compile`
3. `VllmBackend` 截获 FX graph，切图并构建 piecewise backend
4. `CompilerManager` 负责缓存与编译产物落盘
5. 后续运行按 runtime shape 直接命中缓存或已有 compiled callable

### 源码解析

**1. 模块级入口：`support_torch_compile`**

当某个模块被装饰后，首次 `__call__()` 时会进入：

```python
start_monitoring_torch_compile(self.vllm_config)
output = TorchCompileWithNoGuardsWrapper.__call__(self, *args, **kwargs)
```

在此之前，它还会：

```python
_mark_dynamic_inputs(...)
```

并记录：

```python
self.compilation_config.traced_files.add(...)
```

这一步为后续 cache key 计算做准备。

**2. backend 级入口：`VllmBackend.__call__()`**

一旦 Dynamo 把 graph 交给 backend，vLLM 会：

1. 计算 hash / cache_dir
2. 初始化 `CompilerManager`
3. 切图
4. 用 `PiecewiseCompileInterpreter` 安装 piecewise backend

例如：

```python
self.split_gm, self.piecewise_graphs = split_graph(graph, fx_split_ops)
PiecewiseCompileInterpreter(...).run(*fake_args)
```

**3. 编译缓存会综合环境、配置、源码和编译器哈希**

`VllmBackend.__call__()` 里会计算：

- `env_hash`
- `config_hash`
- `code_hash`
- `compiler_hash`

然后决定最终 `cache_dir`。

这说明 vLLM 的编译缓存并不是“只按模型名缓存”，而是严格绑定：

- 环境
- 编译配置
- 被 trace 到的源码内容
- backend / 编译器状态

**4. `CompilerManager.compile()` 会优先 load，失败再 compile**

```python
compiled_graph = self.load(...)
if compiled_graph is not None:
    return compiled_graph

compiled_graph, handle = self.compiler.compile(...)
```

这意味着 runtime 复用路径是编译流程里的一级公民，而不是附带优化。

**5. 如果开启 piecewise cudagraph，还会再包一层 `CUDAGraphWrapper`**

例如在 `PiecewiseCompileInterpreter.call_module()` 中：

```python
self.module.__dict__[target] = static_graph_wrapper_class(
    runnable=piecewise_backend,
    vllm_config=self.vllm_config,
    runtime_mode=CUDAGraphMode.PIECEWISE,
    ...
)
```

所以 vLLM 当前的执行体系实际上是：

**compile 和 cudagraph 交织进行，而不是彼此完全独立。**

另外，`post_init_cudagraph_sizes()` 和 `compute_bs_to_padded_graph_size()` 也说明一件事：

- 编译配置里写下的 `compile_sizes`
- 最终运行时真正 capture / replay 的 padded graph size

并不是完全相同的概念。

vLLM 会先把一组配置化的 size 规范化，再建立“运行时 batch size -> 实际 padded graph size”的映射。因此分析编译命中率时，不能只看原始 batch size，还要看它最终映射到了哪一个 padded graph。

### 代码示例

下面用伪代码把编译流程压出来：

```python
def compiled_forward(*args):
    mark_dynamic_inputs(args)
    fx_graph = dynamo_trace(forward)
    split_graphs = split_graph(fx_graph, splitting_ops)
    compiled_parts = [compile_or_load(g) for g in split_graphs]
    return dispatch_by_runtime_shape(compiled_parts, args)
```

### 完整流程图

```text
                    vLLM 编译流程主链
============================================================================

support_torch_compile module
   |
   v
首次 __call__()
   |
   +--> mark dynamic inputs
   +--> start_monitoring_torch_compile()
   +--> torch.compile(..., backend=VllmBackend)
   |
   v
VllmBackend.__call__()
   |
   +--> compute cache key / cache dir
   +--> split_graph()
   +--> PiecewiseCompileInterpreter()
   +--> CompilerManager.compile()/load()
   |
   v
PiecewiseBackend runtime dispatch
   |
   +--> by compile size / compile range
   +--> (可选) CUDAGraphWrapper
```

## 17.5 编译实例

### 原理讲解

对用户来说，编译配置通常有三层选择：

1. 要不要启用 vLLM 自定义编译
2. 是否和 cudagraph 结合
3. 是否要给出 compile sizes / compile ranges

如果只是想先体验：

- `mode=VLLM_COMPILE`
- `backend=inductor`
- `cudagraph_mode=FULL_AND_PIECEWISE`

通常就是一个比较合理的起点。

### 源码解析

`LLM` 构造函数支持直接传入：

```python
compilation_config: int | dict[str, Any] | CompilationConfig | None
```

这意味着你既可以：

- 传一个整数模式
- 也可以传完整字典

对复杂调优场景，更推荐字典或 `CompilationConfig` 对象，因为它能显式控制：

- `compile_sizes`
- `compile_ranges_split_points`
- `pass_config`
- `cudagraph_mode`

### 代码示例

下面给一个较完整但仍然克制的编译示例：

```python
from vllm import LLM

llm = LLM(
    model="Qwen/Qwen2.5-7B-Instruct",
    compilation_config={
        "mode": "VLLM_COMPILE",
        "backend": "inductor",
        "cudagraph_mode": "FULL_AND_PIECEWISE",
        "compile_sizes": ["cudagraph_capture_sizes"],
        "compile_ranges_split_points": [128, 256, 512],
        "pass_config": {
            "fuse_norm_quant": True,
            "fuse_act_quant": True,
        },
    },
    enforce_eager=False,
)

outputs = llm.generate("Explain piecewise compilation.")
print(outputs[0].outputs[0].text)
```

如果只想快速试一下，也可以用整数模式：

```python
llm = LLM(
    model="Qwen/Qwen2.5-7B-Instruct",
    compilation_config=3,   # VLLM_COMPILE
)
```

### 配置图

========================================================================

mode = VLLM_COMPILE
backend = inductor
cudagraph_mode = FULL_AND_PIECEWISE
compile_sizes = cudagraph_capture_sizes
compile_ranges_split_points = [128, 256, 512]
pass_config = {fusion related flags...}

## 总结

1. `torch.compile` 只是 vLLM 编译体系的底层基础，vLLM 真正的核心在于对 guard、缓存、切图和 runtime dispatch 的增强控制。
2. `CompilationConfig` 是总控配置，`support_torch_compile` 是模块入口，`VllmBackend` 是编译总调度器。
3. piecewise compilation 的目标是把不适合一起编译或一起进入 cudagraph 的部分拆开，再分别管理。
4. `CompilerManager` 让编译缓存成为一等公民，缓存 key 会综合环境、配置、源码和 backend 哈希。
5. `PiecewiseBackend` 不只是“编译多个子图”，还会在运行时按 shape range 和 compile size 分派。
6. vLLM 当前的高性能路径本质上是“compile + piecewise + cudagraph + custom passes”几种机制的组合，而不是单一开关。

5. 结合第9章和本章，说明 cudagraph 和 compile 在 vLLM 里是如何互相配合而不是互相替代的。
