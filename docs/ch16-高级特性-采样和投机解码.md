## 16.1 Transformer 解码与 GPU 性能瓶颈

### 原理讲解

大模型推理的 decode 阶段有一个很典型的问题：

**每一步只生成一个 token，但仍然要为这个 token 跑一整次模型 forward。**

这会带来两个直接后果：

1. **算子粒度太小**
2. **GPU 很难始终处于高吞吐状态**

Prefill 阶段通常是“大批量 token 一起算”，所以更容易把 GPU 跑满。

而 decode 阶段往往是：

- 每个请求一次只向前推进 1 个 token
- 多请求虽然可以拼 batch，但每个请求的 query 长度依然很短
- 结果就是 attention、采样、后处理之间切换频繁

所以 decode 阶段的核心矛盾可以概括成：

**GPU 很强，但自回归解码把工作切得太碎。**

Speculative decoding 的出发点正是：

**不要每次只尝试 1 个 token，而是先批量猜几个，再由目标模型一次性验证。**

### 源码解析

从 vLLM 当前实现看，decode 相关的数据结构已经为 speculative decoding 预留了空间。

在 `GPUModelRunner.__init__()` 中：

```python
if self.speculative_config is not None:
    self.do_spec_decode = True
    self.num_speculative_steps = self.speculative_config.num_speculative_tokens
    self.speculator = init_speculator(self.vllm_config, self.device)
else:
    self.do_spec_decode = False
```

这说明：

- speculative decoding 不是单独的 engine
- 它是 `GPUModelRunner` 上的一条增强执行路径

再看 `prepare_inputs()`：

```python
if not scheduler_output.scheduled_spec_decode_tokens:
    total_num_draft_tokens = 0
else:
    num_draft_tokens = np.array([...], dtype=np.int32)
    total_num_draft_tokens = int(num_draft_tokens.sum())
    total_num_logits = num_reqs + total_num_draft_tokens
```

这表明一旦调度器给出了 speculative draft tokens：

- 这一步 forward 就不只是为“每个请求 1 个 token”算 logits
- 而是会额外为 draft token 预留 logits 位置

### 代码示例

下面用一个最小例子说明普通 decode 和 speculative decode 的差异：

```python
normal_decode = {
    "step1": ["verify t1"],
    "step2": ["verify t2"],
    "step3": ["verify t3"],
}

spec_decode = {
    "step1": ["draft t1,t2,t3", "verify t1,t2,t3 and one bonus token"],
}

print("normal:", normal_decode)
print("spec:", spec_decode)
```

在理想情况下：

- 普通 decode 需要 3 次目标模型 step
- speculative decode 可能 1 次就把这几个 token 都推进完

### 流程图

```text
             自回归解码为什么容易形成瓶颈
========================================================================

普通 decode:
token_1 -> forward
token_2 -> forward
token_3 -> forward
...

问题:
- 每次只推进 1 个 token
- GPU 每步工作粒度小
- 采样 / 通信 / 调度开销占比高

Speculative decoding:
draft token_1..k -> target verify -> 一次接受多个 token
```

## 16.2 推测解码：并行解码的基本框架

### 原理讲解

投机解码（speculative decoding / 推测解码）的基本框架可以压缩成三步：

1. **Proposal**：先生成若干 draft tokens
2. **Verification**：目标模型一次性验证这些 token
3. **Rejection Sampling**：接受前缀一致的部分，并在需要时恢复目标分布

最关键的点在于：

**draft 模型可以不完全准确，但最终输出分布必须与目标模型保持一致。**

这也是为什么 speculative decoding 里 rejection sampling 不是可选优化，而是 correctness 的核心部分。

### 源码解析

`SpecDecodeMetadata` 基本把这套框架所需的索引信息都放进去了：

```python
@dataclass
class SpecDecodeMetadata:
    draft_token_ids: torch.Tensor
    num_draft_tokens: list[int]
    cu_num_draft_tokens: torch.Tensor
    cu_num_sampled_tokens: torch.Tensor
    target_logits_indices: torch.Tensor
    bonus_logits_indices: torch.Tensor
    logits_indices: torch.Tensor
```

这几个字段的含义可以简单理解为：

- `draft_token_ids`：本轮提出的 draft token
- `cu_num_draft_tokens`：每个请求 draft token 的前缀和
- `target_logits_indices`：哪些 logits 用来校验 draft token
- `bonus_logits_indices`：如果全部接受，还要额外拿哪个 logits 生成 bonus token

再看 `RejectionSampler.forward()`：

```python
bonus_sampler_output = self.sampler(...)
target_logits = self.apply_logits_processors(...)
target_probs = target_logits.softmax(dim=-1, dtype=torch.float32)

output_token_ids = rejection_sample(
    metadata.draft_token_ids,
    metadata.num_draft_tokens,
    metadata.max_spec_len,
    metadata.cu_num_draft_tokens,
    draft_probs,
    target_probs,
    bonus_token_ids,
    sampling_metadata,
)
```

这里已经能看到完整结构：

1. 先准备 bonus token
2. 再得到目标模型对 draft 位置的概率
3. 最后做 rejection sampling

源码注释里还专门区分了四种 token：

- accepted tokens
- recovered tokens
- bonus tokens
- output tokens

这个划分非常重要，因为它直接说明：

**最终输出 token 并不等于“draft token 里被接受的那一部分”，它还可能包含恢复采样出的 token 和 bonus token。**

### 代码示例

下面用一个极简例子模拟 speculative decoding 的验证逻辑：

```python
draft = ["A", "B", "C"]
target = ["A", "B", "X"]

accepted = []
for d, t in zip(draft, target):
    if d == t:
        accepted.append(d)
    else:
        accepted.append(t)
        break

print("draft:", draft)
print("target:", target)
print("accepted prefix + recovery:", accepted)
```

真实 rejection sampling 要比“逐个相等比较”更严格，因为它是按概率分布来恢复正确性，而不只是字面比较。

### 数据流图

```text
              speculative decoding 基本框架
========================================================================

draft proposer
   |
   v
draft tokens
   |
   v
target model verify logits
   |
   v
rejection sampler
   |
   +--> accepted tokens
   +--> recovered tokens
   +--> bonus token
   |
   v
final output tokens
```

## 16.3 Medusa：无 Draft 小模型的多头并行解码

### 原理讲解

Medusa 的核心思想是：

**不再额外引入一个独立 draft 小模型，而是在目标模型旁边挂多个预测头，直接基于目标模型隐藏状态提出多个未来 token。**

这样做的好处是：

- 避免单独部署一套 draft 模型
- 不需要维护目标模型和 draft 模型之间的 tokenizer / vocab / 并行配置兼容性

它的代价是：

- 需要额外的 Medusa 头参数
- draft proposal 的质量强依赖这些头与主模型的协同训练情况

### 源码解析

`v1/spec_decode/medusa.py` 里的 `MedusaProposer` 非常直白：

```python
blocks = self.model(target_hidden_states)
logits = self.model.compute_logits(blocks)
draft_tokens = torch.stack([logit.argmax(dim=-1) for logit in logits], dim=1)
```

这里可以直接看出 Medusa 的 proposal 方式：

1. 输入不是 prompt token，而是目标模型算出来的 `target_hidden_states`
2. `self.model` 返回多个 head 的 block 输出
3. 每个 head 各自产生一个未来 token 的 logits
4. 最后把多个 head 的 argmax 堆起来，得到 `[batch_size, num_heads]` 的 draft token

再看 `load_model()`：

```python
with set_model_tag("medusa_head"):
    self.model = get_model(...)
```

这说明在编译和缓存视角里，Medusa 头被当成模型的一个独立子部件来处理。

这里还要补一个容易混淆的边界：

- `v1/spec_decode/medusa.py` 里已经有 `MedusaProposer`
- 但当前 `v1/worker/gpu/spec_decode/__init__.py` 的 `init_speculator()` 只在 `use_eagle()` 为真时返回 `EagleSpeculator`

也就是说，从当前 v1 worker 主执行链来看，接入最完整的是 Eagle/Eagle3/MTP 这一支。Medusa 在 proposal 目录里已经有实现，但它并不是通过当前这条 `init_speculator() -> EagleSpeculator` worker 路径落地的。

### 代码示例

下面用一个最小例子说明 Medusa 风格的多头 proposal：

```python
hidden_state = "h_t"

medusa_heads = {
    "head_1": "predict next token",
    "head_2": "predict token t+2",
    "head_3": "predict token t+3",
}

print(hidden_state)
print(medusa_heads)
```

它和 draft model 最大的区别是：

- draft model：再跑一套小模型
- Medusa：直接复用目标模型当前隐藏状态

### 架构总览

```text
                  Medusa 的 proposal 方式
========================================================================

target hidden states
   |
   +--> medusa head 1 -> token t+1
   +--> medusa head 2 -> token t+2
   +--> medusa head 3 -> token t+3
   |
   v
draft token matrix [batch, num_heads]
```

## 16.4 Eagle 投机解码

### 原理讲解

EAGLE 系列方法的核心不是“多头一起猜”，而是：

**用一个专门的 proposer / speculator 模型，在目标模型隐藏状态基础上迭代地产生多步草稿。**

从当前 vLLM 源码看，EAGLE/EAGLE3/MTP 是 worker 侧接入最完整的一条 speculative 路径。

### 源码解析

**1. worker 侧 `init_speculator()` 当前直接接入的是 Eagle 路径**

```python
def init_speculator(vllm_config, device):
    speculative_config = vllm_config.speculative_config
    if speculative_config.use_eagle():
        from vllm.v1.worker.gpu.spec_decode.eagle import EagleSpeculator
        return EagleSpeculator(vllm_config, device)
    raise NotImplementedError(...)
```

`use_eagle()` 在 `SpeculativeConfig` 里定义为：

```python
def use_eagle(self) -> bool:
    return self.method in ("eagle", "eagle3", "mtp")
```

这说明就当前 v1 GPU worker 主链而言：

- `eagle`
- `eagle3`
- `mtp`

会进入统一的 `EagleSpeculator` 执行路径。

**2. `EagleProposer` 负责 proposal 侧的模型组织与输入准备**

在 `v1/spec_decode/eagle.py` 里，`EagleProposer` 会准备：

- `input_ids`
- `positions`
- `hidden_states`
- tree-based speculative token structure

例如：

```python
self.num_speculative_tokens = self.speculative_config.num_speculative_tokens
self.tree_choices = ast.literal_eval(spec_token_tree)
```

这说明 EAGLE 在当前实现里已经不只是“线性猜几个 token”，而是支持 token tree。

**3. `EagleSpeculator` 负责 worker 侧真正的 draft 生成**

在 `v1/worker/gpu/spec_decode/eagle.py` 里，`propose()` 是主入口：

```python
draft_tokens = self.speculator.propose(
    input_batch,
    sampling_metadata,
    last_hidden_states,
    aux_hidden_states,
    num_sampled,
    num_rejected,
    last_sampled_tokens,
    next_prefill_tokens,
)
```

它会先准备 speculator 输入，再调用：

```python
last_hidden_states, hidden_states = self.run_model(...)
logits = self.model.compute_logits(sample_hidden_states)
draft_tokens = gumbel_sample(...)
```

然后如果 `num_speculative_steps > 1`，继续迭代生成更多 draft token。

**4. rejection sample kernel 在 worker 侧用 Triton 实现**

`v1/worker/gpu/spec_decode/rejection_sample.py` 的 Triton kernel 做的事情很直接：

```python
for i in range(num_tokens - 1):
    if target_sampled != draft_sampled:
        rejected = True
```

虽然高层 `RejectionSampler` 负责完整分布恢复，但 worker 侧也有一版更直接的 token 级 rejection sample kernel，用于高效统计每个请求究竟接受了几个 speculative token。

### 代码示例

下面给一个最小的 Eagle speculative 配置示例：

```python
speculative_config = {
    "method": "eagle",
    "model": "yuhuili/EAGLE-LLaMA3.1-Instruct-8B",
    "num_speculative_tokens": 3,
}

print(speculative_config)
```

如果是同模型上的 MTP 路径，配置通常只需要：

```python
speculative_config = {
    "method": "mtp",
    "num_speculative_tokens": 2,
}
```

### 流程图

```text
                   Eagle 路径的主结构
========================================================================

target hidden states
   |
   v
EagleSpeculator.propose()
   |
   +--> prepare_eagle_inputs(...)
   +--> run_model(...)
   +--> compute_logits(...)
   +--> gumbel_sample(...)
   |
   v
draft tokens
   |
   v
target verify + rejection sample
```

## 16.5 推测解码的分类 & 设计

### 原理讲解

从当前仓库里的 `SpeculativeMethod` 定义来看，vLLM 把 speculative decoding 至少分成了几类：

1. **无模型 proposal**
2. **附加 head proposal**
3. **独立 / 半独立 draft model proposal**
4. **基于缓存结构的 pattern proposal**

### 源码解析

`config/speculative.py` 里直接给出了方法枚举：

```python
SpeculativeMethod = Literal[
    "ngram",
    "medusa",
    "mlp_speculator",
    "draft_model",
    "suffix",
    EagleModelTypes,
]
```

可以据此把当前实现大致分类为：

- `ngram`
  - 不依赖额外模型
  - 基于 prompt / output token 重复模式提案
- `suffix`
  - 依赖 suffix tree / cache
  - 也是无额外神经网络 proposal
- `medusa`
  - 用多个 head 基于目标 hidden states 直接提案
- `eagle / eagle3 / mtp`
  - 用单独的 proposer / speculator 路径生成多步草稿

再看 `NgramProposer`：

```python
draft_token_ids = self.batch_propose(...)
```

它依赖的是：

- `prompt_lookup_min`
- `prompt_lookup_max`
- `num_speculative_tokens`

本质上是“从已有 token 序列里找最长匹配片段，再把后续 token 拿来当草稿”。

`SuffixDecodingProposer` 则把这个思路做得更进一步：

```python
self.suffix_cache = SuffixDecodingCache(...)
draft = self.suffix_cache.speculate(...)
```

它会维护请求级 suffix tree，因此 speculative 长度可以动态变化，不再固定为同一 `k`。

除了“方法枚举”本身，`SpeculativeConfig.__post_init__()` 还承担了不少真正决定运行行为的工作：

- 如果方法是 `ngram`、`suffix`、`mtp`，它会补齐一部分默认配置
- 如果给了 `model`，它会进一步构造 `draft_model_config`
- 它会校验 draft TP，要求要么是 `1`，要么和 target TP 一致
- 它会整理 `speculative_token_tree`，让 Eagle/Eagle3 这类 tree proposal 在运行时直接可用

所以 `SpeculativeConfig` 在 vLLM 里并不只是“把参数存起来”，而是：

**在 engine 真正开始跑之前，把 speculative decoding 的方法、并行约束和 token tree 都先规范化。**

### 代码示例

下面给出一个按设计思想分类的最小示意：

```python
spec_methods = {
    "ngram": "从已有 token 模式里找可重复片段",
    "suffix": "从 suffix tree / cache 里找可扩展后缀",
    "medusa": "从目标 hidden state 的多头输出直接猜未来 token",
    "eagle": "用专门 proposer 模型迭代地产生 draft token",
    "mtp": "利用同模型中的多 token prediction 能力做自投机",
}

print(spec_methods)
```

### 分类图

```text
                 当前 vLLM speculative 方法的设计谱系
============================================================================

无模型 proposal:
- ngram
- suffix

附加 head:
- medusa

独立 / 半独立 proposer:
- eagle
- eagle3
- mtp
```

## 16.6 vLLM 中的投机采样

### 原理讲解

proposal 只解决“先猜几个 token”，真正把输出分布校正回目标模型的是：

**投机采样 / rejection sampling。**

在 vLLM 里，这部分逻辑并没有散在 proposer 里，而是被单独封装成 `RejectionSampler`。

### 源码解析

`RejectionSampler` 的类注释直接说明它遵循的是经典 speculative decoding 论文算法。

它内部最值得关注的几个步骤是：

**1. 先对 bonus token 做正常采样**

```python
bonus_sampler_output = self.sampler(...)
bonus_token_ids = bonus_sampler_output.sampled_token_ids
```

**2. 对 target logits 应用处理器和采样约束**

```python
target_logits = self.apply_logits_processors(raw_target_logits, sampling_metadata, metadata)
target_logits = apply_sampling_constraints(target_logits, ...)
target_probs = target_logits.softmax(dim=-1, dtype=torch.float32)
```

这里特别关键，因为这说明 speculative decoding 不是“跳过采样逻辑”，而是：

- bad words
- penalties
- allowed token ids
- top-k / top-p 等约束

仍然要被正确地应用到 target logits 上。

**3. 最后才进入 rejection sample**

```python
output_token_ids = rejection_sample(
    metadata.draft_token_ids,
    metadata.num_draft_tokens,
    metadata.max_spec_len,
    metadata.cu_num_draft_tokens,
    draft_probs,
    target_probs,
    bonus_token_ids,
    sampling_metadata,
)
```

也就是说，proposal 与 sampling 在 vLLM 里是两段：

- proposer：给出 draft candidates
- rejection sampler：恢复正确分布并输出最终 token

**4. 输出还会再被 `parse_output()` 转回每个请求的 token 序列**

```python
outputs = [row[valid_mask[i]].tolist() for i, row in enumerate(output_token_ids_np)]
```

这一步会把 placeholder token 过滤掉，只保留真正接受 / 恢复出来的 token。

### 代码示例

下面用一个最小例子模拟“接受 + 恢复 + bonus”三种来源：

```python
accepted = ["A", "B"]
recovered = ["X"]
bonus = ["Y"]

final_output = accepted + recovered + bonus
print(final_output)
```

真实实现里：

- `accepted` 来自 draft 与 target 的一致前缀
- `recovered` 来自 rejection sampling 的分布恢复
- `bonus` 只在全部 draft 都被接受时才加入

### 数据流图

```text
                    vLLM 中的投机采样
========================================================================

draft_probs / draft_token_ids
          +
target_logits
   |
   v
RejectionSampler.forward()
   |
   +--> 采样 bonus token
   +--> 应用 logits processors / penalties / bad words
   +--> target_probs softmax
   +--> rejection_sample(...)
   |
   v
final output tokens
```

## 16.7 投机解码核心组件与目录结构

### 原理讲解

当前 vLLM 的 speculative decoding 相关代码不是都堆在一个目录里，而是分成了四层：

1. **配置层**
2. **proposal 算法层**
3. **worker GPU 执行层**
4. **采样 / 校验层**

### 源码解析

可以把当前目录结构压成下面这样：

```text
config/speculative.py
    - SpeculativeConfig

v1/spec_decode/
    - eagle.py
    - medusa.py
    - ngram_proposer.py
    - suffix_decoding.py
    - metadata.py
    - metrics.py

v1/worker/gpu/spec_decode/
    - __init__.py
    - eagle.py
    - eagle_cudagraph.py
    - rejection_sample.py

v1/sample/
    - rejection_sampler.py
```

它们各自负责：

- `config/speculative.py`
  - 方法选择
  - draft model 配置
  - speculative token tree
  - TP/并行校验

## 16.8 推理主流程总览

### 原理讲解

把当前仓库里 speculative decoding 的运行链路压缩一下，大致就是：

1. 调度器把 draft token 一起安排进本轮 batch
2. `GPUModelRunner.execute_model()` 准备好 input batch 和 logits 索引
3. 目标模型 forward 产生 draft 位置和 bonus 位置的 logits
4. `sample()` 里做 rejection sampling，决定本轮真正接受多少 token
5. `postprocess()` 更新请求状态
6. `propose_draft()` 再为下一轮生成新的 draft token

### 源码解析

最关键的主链在 `GPUModelRunner.sample_tokens()`：

```python
sampler_output, num_sampled, num_rejected = self.sample(...)
...
self.postprocess(...)
if self.do_spec_decode:
    draft_tokens = self.propose_draft(...)
    self.req_states.draft_tokens[input_batch.idx_mapping] = draft_tokens
```

这段逻辑非常值得记住，因为它说明 speculative decoding 在 vLLM 当前实现里是一个闭环：

**本轮先验证旧 draft，再生成下一轮 draft。**

再看 `sample()`：

```python
sampler_output = self.sampler(logits, sampling_metadata)

if input_batch.num_draft_tokens > 0:
    sampled_tokens, num_sampled = rejection_sample(
        sampler_output.sampled_token_ids,
        input_ids,
        input_batch.cu_num_logits,
        self.num_speculative_steps,
    )
```

这里说明：

- 目标模型本轮已经把 draft 位置对应的 logits 都算出来了
- 真正决定“本轮推进多少 token”的，是 rejection sample

最后 `prepare_inputs()` 里：

```python
logits_indices = combine_sampled_and_draft_tokens(...)
```

这一步把“上轮接受的 token”和“本轮待验证的 draft token”拼成新的 logits 访问布局。

### 代码示例

下面用伪代码把整条主链压出来：

```python
def one_spec_decode_step():
    input_batch = prepare_inputs()
    hidden_states = target_model_forward(input_batch)
    sampled_tokens, num_sampled = rejection_sample_from_target_logits(hidden_states)
    postprocess(sampled_tokens, num_sampled)
    next_draft_tokens = propose_draft_for_next_step()
    return sampled_tokens, next_draft_tokens
```

## 总结

1. speculative decoding 要优化的是 decode 阶段“每步只推进 1 个 token”带来的 GPU 低吞吐问题。
2. 它的基本框架是 `proposal -> target verification -> rejection sampling`，其中 rejection sampling 负责保证输出分布正确。
3. 当前仓库里的 speculative 方法至少包括 ngram、suffix、Medusa、EAGLE/EAGLE3/MTP 几类，分别对应不同 proposal 设计。
4. `SpecDecodeMetadata` 负责索引组织，`RejectionSampler` 负责正确性恢复，`GPUModelRunner` 负责把 speculative 路径接进主执行循环。
5. 从当前 v1 GPU worker 主链看，`EagleSpeculator` 是最完整接入 worker 执行面的 speculative 路径。
6. speculative decoding 不是“单纯多猜几个 token”，而是一套围绕 proposal、verification、acceptance length 和下一轮草稿缓存组织起来的闭环执行机制。

## 思考题

1. 为什么 speculative decoding 能提升 decode 吞吐，但不一定总能提升端到端时延？
2. `SpecDecodeMetadata` 里为什么要区分 `target_logits_indices` 和 `bonus_logits_indices`？
3. Medusa 和 Eagle 都能一次提出多个 draft token，它们在“是否依赖额外 draft 模型”上有什么根本区别？
4. 为什么 rejection sampling 是 speculative decoding 的 correctness 核心，而不是一个可选优化？
5. 从当前源码看，proposal 逻辑和 worker 侧 speculator 逻辑为什么要拆到两个目录层级里？
